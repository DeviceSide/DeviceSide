# v0.2.0: open light features outside Labs, show users their coverage, release

2026-11-25. Agreed with Jason in the planning session; branch `wt/v0.2.0-backlog`.

## Context

Asking users to turn on Labs is friction. Most Zigbee lights take the same standard calls (moveToLevel, stop, attribute
writes and reads), yet `docs/evidence.md` keeps the default class `other` in Labs on every write: it is Documented only
by a certified read, and a write never qualifies. #607 fixed the bridge cache crash that left every non-Hue Z2M device
Unplaced, so Z2M's records since it broke want a full rerun. PR #609 is taking the Aqara color bulb to Verified.

## Decisions (interview, 2026-11-25)

1. **Standard-call route to Documented.** Amend `docs/evidence.md`: a light write whose call is the Zigbee 3.0 / ZLL
   standard command, and whose failure is low harm (lights only; harm lives in switch, plug and relay loads), is
   Documented on a class keyed on a certification marker. A failing report splits that identity off as `NotBuilt`.
   No new level. This is a binding-rule change: its own PR, an Opus auditor.
2. **Split from #609.** #609 keeps the Aqara Verified work (its steps 1-5); its step 6 (vendor research, the rule call)
   moves here. Either PR can land first.
3. **Install coverage view: prototype, then pick.** A throwaway prototype of two or three surfaces on Jason's HA device
   list; Jason picks one; it ships in this release.
4. **The release is v0.2.0rc1.** Its RC audit is `docs/audits/v0.2.0rc1.md`, covering everything since v0.1.0 (the
   v0.1.1rc1 record is superseded). v0.1.0 shipped, so the 7-day soak applies before `cut-release`.

## Decisions (step 2 grilling, 2026-11-25)

From [the converter survey](../research/2026-11-25-z2m-converter-survey.md).

5. **The marker is the ZHC definition** (survey Part 5, option 1). A table of `definition.model` → traits, generated
   from a pinned zigbee-herdsman-converters (ZHC) commit and committed. No certification marker exists, and
   ClusterRevision went unread in the partial probe.
6. **Architecture: the vendor families stay, plus one new Z2M class** carved out of `other` by one rule after the
   families. Membership is strict: no flag or override touching any DeviceSide call (642 of `other`'s 848 light
   definitions at the survey's pin). The bump check also flags trait changes on family models, without classifying by
   them.
   - A trait-driven redesign (every class a ZHC trait set) was debated and rejected:
     - traits describe ZHC's converters, not firmware;
     - most known failures carry no trait;
     - Tuya still needs Zigbee-string rules;
     - ZHA has no ZHC traits;
     - a trait class has no owner.
   - What would reopen it: hardware records showing that same-trait lights from different vendors pass and fail
     together, while same-vendor lights split by trait. Widening membership per action (Innr, ADEO) later is a
     predicate change on the same table.
7. **Usage is documentation, on Z2M only.**
   - A converter implemented in Z2M documents its call through usage, unless Z2M or ZHC issues or PR comments report
     particular devices or vendors departing.
   - ZHA's usage is not documentation: its user base is smaller, and its code is less well maintained and buggier, from
     the rig's experience. So the route is Z2M-only this release, and ZHA keeps its levels.
8. **Qualifying actions, Documented on the new class:**
   - `raise_brightness`, `lower_brightness` and `stop`;
   - `raise_hue`, `lower_hue`, `raise_saturation` and `lower_saturation`, only on lights whose exposes include
     `color_hs`;
   - `set_attributes` and `get_attributes`. These two aren't on usage (ZHC sends options 0/0; DeviceSide sends 1/1).
     They qualify because every known failure is visible: MALFORMED_COMMAND, a failed read-back, UNSUPPORTED_ATTRIBUTE.
     The one silent case, `disableDefaultResponse`, is outside the class.
9. **The brightness floor is #613's.** ZHC's `turnsOffAtBrightness1` rewrites level 1 to 2, and #613 owns the
   internals note, the Hue bypass and the rig case at the bottom. The 132 `other` definitions with the flag stay out of
   the new class. Step 3 depends on #613.
10. **Split-offs, three paths:**
    - **ZHC adds a flag or an override:** the table regeneration proposes the model's departure (Decision 11).
    - **A Z2M or ZHC issue or PR reports the device failing a call DeviceSide sends:** the model is excluded on the
      report alone, citing it.
    - **A DeviceSide report:** evidence.md's contrary-evidence rules, unchanged.

    The identity is the narrowest the report supports: the definition model by default, or the Zigbee model ID with
    manufacturer and firmware where the report narrows it. Survey Part 4's unflagged rows enter in step 3:
    - dresden FLS-PP3;
    - Paulmann 924.70;
    - Müller Licht GU10;
    - AwoX, EGLO EGLO_ZM_RGB_TW and Iluminize 5120.1100;
    - Müller Licht tint on older firmware.
11. **Membership changes on a ZHC bump.**
    - The bump check proposes additions and departures; additions enter on the maintainer's merge.
    - A departure needs a maintainer's review only for a model whose features shipped outside Labs in a tagged full
      release, as withdrawing a feature users rely on without notice is a bad experience. The maintainer keeps it, with
      the reason, or excludes it, with a source.
    - Models still behind Labs, or added and removed between tagged full releases, leave without review.
12. **Split-offs are held in the class's own committed list:** an `excluded` section, one row per model, with the
    action and its source. An excluded model stays in `other`, in Labs, on every action. That costs per-action
    precision on about 7 models.
    - `not_built` isn't widened. `docs/design.md`'s scope table limits it to a class today's call would harm, on an
      action whose failure harms, and the registry checks that.
    - Widen it later only if per-action split-offs pile up.
13. **The README fold is unchanged.** The cap went in #594. The new class's line is 🟡 and stands alone; what stays in
    `other` folds as now.
14. **Card and list.** The class's phrase is "other brands' standard lights", its section `### Standard lights` in
    Zigbee2MQTT's `index.md`: what sets it apart, why it is Documented, and how a user checks (the light's Model on
    its Zigbee2MQTT page, or the coverage view). A generated `docs/integrations/zigbee2mqtt/standard-lights.md` lists
    the members, with a hue and saturation column, and the excluded rows with their sources; `--check` proves it.
    `other`'s light phrase stays, and its section points to Standard lights.
15. **One class, not two.** Hue and saturation are Documented on the whole class: `zigbee2mqtt/fade.py`'s
    `color_hs` check already answers `unchanged` with `fields_dropped` for a light without it, so no move reaches one.
    A unit test pins it.
16. **The ZHC bump is a release step.**
    - The release skill's first item for each RC, before `/rc-audit`: `scripts/zhc_table.py --pin <ZHC release tag>`,
      a bump PR whose body is the proposal, its departures reviewed there, merged before the audit covers it.
    - A guard in `cut-release-candidate` (git reads only) fails an RC from `main` whose table pin is unchanged since
      the previous RC tag, unless its audit record says `ZHC bump skipped: <reason>`. Fix branches are exempt.
    - No bump between an RC and its release; PR CI never clones ZHC.

## Steps

1. **The marker** (opus orchestrates; `/research`). Question: what on a Z2M or ZHA device tells that a light takes the
   standard calls, so step 2 can key the route on it. #609's `docs/research/2026-11-25-vendor-call-documentation.md`
   already covers vendors and certification: no vendor publishes its calls; the CSA test specs LC-TC-07S and CC-TC-09S
   send DeviceSide's exact ExecuteIfOff moveToLevel and moveToColor; Move, Stop and Step with ExecuteIfOff are assumed,
   not run; only mandatory attributes are sure to be read. Extend it, don't redo it. Four parts:
   - **A. Converter table** (sonnet, a script, not agents reading files). Clone zigbee-herdsman-converters (ZHC) to the
     scratchpad at a pinned commit; extract one row per light definition: vendor, fingerprints (`zigbeeModel`,
     `fingerprint`), the light extend and its arguments, `meta` quirk flags (`turnsOffAtBrightness1`,
     `noOffTransition`, `applyRedFix`, `supportsHueAndSaturation`, …), custom `toZigbee` overrides, white-labels.
     Report the share of lights on the plain standard extend with no flag touching DeviceSide's calls. A low share
     ends the survey after C.
   - **B. Issue mining** (2-3 sonnet agents, split by call, not vendor): fades and transitions; stop and raw `command`
     writes (ExecuteIfOff, set while off); attribute reads (one unsupported attribute failing a read). Bounded
     `gh search issues` on Koenkk/zigbee2mqtt and Koenkk/zigbee-herdsman-converters. Per issue: device, symptom,
     root cause, the fix (flag or override added), link. They catalog; they don't judge.
   - **C. Synthesis** (opus). Per DeviceSide action: the path it rides (fades: Z2M's `transition` and `*_move`
     converters, so Z2M's users already send the same call; `stop` and `set_attributes`: a raw `command` DeviceSide
     builds), the definitions whose flags or overrides touch it, known failures. Output: candidate `NotBuilt`
     entries with their source; the share of lights each candidate marker covers; the marker options (a ZHC
     definition on the standard extend with no flag touching the call; certification; anything a device field gives,
     tried read-only on Jason's devices through ha-rig's HAClient); which DeviceSide classes already pass the calls,
     from the records.
   - **D. Write-up:** `docs/research/2026-11-2x-z2m-converter-survey.md`, citing the ZHC commit and issue links only
     (public sources; nothing from Jason's devices but anonymized results). Then stop: step 2 is Jason's grilling.
   A missing flag means unreported, not tested: say so where a marker leans on it.
2. **Rule call** (planning session, opus, with Jason via `/grilling`). Settle the Open list from step 1's file; record
   the answers here as Decisions 5+. Then write the step 3 sub-plan below.

   `integrations/zigbee2mqtt/classes.py` and `families/` if step 2 keys on vendors; `documented(...)` in place of
