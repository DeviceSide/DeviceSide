# Slice 15: the lab

Agreed with Jason on 2026-11-01. It builds on the A60 move probe ([`2026-10-31-a60-move-probe.md`](2026-10-31-a60-move-probe.md))
and replaces the sweep plan's `--move` command and hand-edited inventory
([`2026-10-30-rig-coverage-sweep.md`](2026-10-30-rig-coverage-sweep.md), phase A0 and A).

## Why

Today every rig entity is an in-use house light, listed in one gitignored `inventory.yaml`, and the A60 moves
between Zigbee networks by hand. The lab is three lamps in the maintainer's own room, which no one else uses, near
the bridge and the coordinators. They hold a Hue white ambiance bulb, a Hue White bulb and the A60, Hue's color
bulb. The rig moves them between Hue, ZHA and Z2M within one run, so color and group suites run while the rest of
the house is in use, with no manual moves and no test fixtures left in the house.

The house stays a second setup, for the run before each release: the mesh, a second brand (the Sengleds) and mixed
groups. Records say which setup ran. Hue's group and scene cases run only on the lab, on its rig-made zone and
scene: the house's hand-made Hue zone and scene are retired (Jason, 2026-11-01), so a house run doesn't cover them.

## Decisions

- **Profiles.** One `.env.rig` per Home Assistant instance holds what belongs to it: address, tokens, deploy
  commands, Hue bridge. Everything about a test setup is one **profile**, `tests/rig/profiles/<name>.yaml`
  (gitignored; `tests/rig/profile.example.yaml` tracked): entities by integration and role, `pause:` (formerly `RIG_PAUSE`), and the
  lab's `roam:`. `--profile` picks one, and can be left out while there is only one. Profiles: `lab` and `house`.
  Test records gain a `Profile` row.
- **The A60 is the lab's color bulb.** It moves into the lab, and the remaining A60 runs (13k) become lab runs.
- **Roam within one run.** All lab bulbs move together, directly from network to network, visiting only the
  networks whose suites the run includes (in the order Hue, ZHA, Z2M). Each network's suites run while the bulbs
  are there, and the run ends with them home on Hue. A run that needs only Z2M goes Hue → Z2M → Hue;
  `--roam-check` visits all three. Direct moves are allowed and preferred (Jason, 2026-11-02): the bring-up moved
  bulbs ZHA → Hue and Z2M → Hue directly.
- **Hue is home.** Before the bulbs first leave, the run saves each one's room membership and the scene actions
  that target it. After the return it adds the new device to the room and rewrites those actions against the
  bulb's new light ID.
- **Fixed HA entity IDs.** After every join the bulb is renamed to its profile entity ID, so automations and
  dashboards survive.
- **Rig-made groups, zones and scenes** are named `ds-rig-*`, made on each visit, removed after it and by
  `--recover` after a crash. A Hue-only lab run makes them on Hue without moving the bulbs.
- **Recovery moves the bulbs home.** `--recover`, and the next run's replay before its gate, move each bulb
  straight home to Hue, from wherever it is, and restore the room. A bulb on no network stops recovery with the Hue app's
  Bluetooth-reset instruction and keeps the journal.
- **No plugs on the lamps.** The lamps' inline switches stay on, and the rig's availability check stops a run on a
  lamp that's switched off. Power-loss cases are out of scope. Switch tests stay on the Shelly relays and the
  Matter plug.
- **The room's automations** go in the lab profile's `pause:`.
- **Order:** slice 15 lands before the Z2M A60 run.

## Profile format

```yaml
pause: [automation.…, switch.…]   # automations and switches only

shelly: […]                        # fixed entities by integration, as before
matter: […]

roam:                              # the lab only (PR 3)
  bulbs:
    - ieee: "…"                    # finds the device on every network
      entity_id: light.…           # its fixed HA entity ID
      roles: [light_dimmable, light_ct, light_color]
      z2m_options: {…}             # set again after each Z2M join: Z2M's remove drops them
  groups:                          # ds-rig-* native groups made on each visit (PR 4)
    - entity_id: light.…           # ds-rig-<object ID> on the network, renamed to this
      roles: [group]               # group or group_color, each on one group
      members: all                 # or bulb entity IDs: the A60 alone for group_color
      scene: scene.…               # optional, group role only: a Hue scene in the zone, the scene role
```

## PRs

1. **Profiles.** `tests/rig/inventory.py` becomes `tests/rig/profile.py` (`Profile`, `profile_paths`);
   `--profile`; `pause:` in the profile; a leftover `inventory.yaml`, or `RIG_PAUSE` in `.env.rig`, stops the run
   with how to move it. The journal names the run's profile, and test records gain a `Profile` row. The household
   check reads every profile's entity IDs, members, supplies and pause list.
2. **Network clients**, unused until PR 3: Hue CLIP v2 `get`, `post` and `delete` beside `put`; ZHA `permit`
   (always closed with `duration: 0`; its state can't be read) and `remove`; Z2M `permit_join`, its state from
   `bridge/info`, and device remove, over MQTT as `set_z2m_device_options` does; entity registry rename and remove;
   a device lookup by IEEE on each network.
3. **Roaming** (`tests/rig/roam.py`). A move releases each bulb from its network and joins them all to the
   target, per the probe; bulbs are released last joined first (see the bring-up findings):

   | Network | Release | Join |
   |---|---|---|
   | Hue | CLIP v2 `DELETE device/<id>` (found by IEEE in `zigbee_connectivity`) | one CLIP v2 `zigbee_device_discovery` search (about 56 s; it can't be ended early) |
   | ZHA | `zha.remove` | `zha.permit` 120 s, then `duration: 0` |
   | Z2M | Z2M `bridge/request/device/remove` | `permit_join` 120 s, closed once all have joined |

   Before opening a network, check the other two are closed; abort if a bulb hasn't joined in 120 s (Hue: after a
   second search, made only when a bulb is still missing as the first ends; a device that joins and isn't a lab bulb is
   named). After each
   join: wait for the device in HA by IEEE, remove a stale registry entry holding the fixed ID, rename, and on Z2M
   set `z2m_options`. A `roam` journal section is written before each move: where each bulb is, the move in
   flight, the saved home. Suites run in phases: Hue, with the fixed integrations (Shelly, Matter);
   then ZHA; then Z2M, skipping a network with no suites in the run. Each phase waits for its targets, runs its automated cases and then its observed ones, so an
   attended run is watched up to three times. The plan before the gate lists the moves and join windows.
   `--roam-check` visits every network with no suites.
4. **`ds-rig-*` groups, zones and scenes** on each visit: a Z2M group, a ZHA group, a Hue zone (its
   `grouped_light` is the group) and a Hue scene in it for the `scene` role (each member on at 40 %, 366 mirek
   where it takes a color temperature). Each is journaled before it is made, renamed to its fixed entity ID (and
   enabled, if HA added it disabled), and removed before the bulbs move on; an entity HA keeps after its group goes
   is removed too. A fixed ID something else holds, or a `ds-rig-*` name already on the network, stops the run
   before that group is made; the groups already made go, and the bulbs still move home. `--roam-check` makes and removes them on every visit. HA's entity is found by the
   group's identifiers, unverified until PR 5: Hue by the grouped_light or scene ID as unique_id, ZHA by
   `light_zha_group_0x<id>`, Z2M by its group device. This replaces the sweep plan's hand-made temporary Z2M
   group, and the house's hand-made Hue zone and scene.
5. **Lab bring-up**, attended, and every rig run needs Jason's go: the A60 moves into the lab; Jason writes
   `profiles/lab.yaml`; a `--roam-check` round trip is the first probe of the white ambiance and White bulbs
   (firmware recorded) and measures what each move leaves in HA's registries. The findings go here, with no
   serials, IEEEs or names.

## Bring-up findings (PR 5, 2026-11-02)

**Firmware**, as the bridge reported it: Hue White (LWA012) 1.104.2, Hue white ambiance (LTA009) 1.163.1, the A60
(LCA016) 1.164.2. Z2M showed the same builds for the first two once interviewed. The White's old firmware made no
difference: it took every Leave and joined each network as fast as the others.

**What each move leaves in HA's registries:**

| Leaving | What HA does | Rejoining |
|---|---|---|
| Hue (CLIP v2 device delete) | drops the device, its light and its connectivity sensor within seconds; nothing orphaned | the light gets a generated ID (`light.hue_white_lamp_1_7` and the like), renamed back; the sensor returns under its old ID |
| ZHA (`zha.remove`) | drops the device and all its entities at once, whether or not the bulb takes the Leave | about 7 or 8 entities with model-based IDs; HA restores an earlier ID it remembers by unique_id, and the recorder warns it can't migrate history to an ID already in use |
| Z2M (device remove) | drops the device and its entities once Z2M confirms the remove | 8 entities named after the IEEE (`light.0x…`), renamed back |

HA keeps a re-added device's original `created_at`, so the registry can't tell join order.

**Joins.** Hue → ZHA and ZHA → Z2M took about 10 s per bulb; the bulbs joined Hue on the first search once nothing
was in the way. A full `--roam-check` round trip with its groups takes about 2 min 10 s.

**Missed Leaves: release last joined first.** A bulb often joins through a lab bulb that joined before it (the
coordinator logs the parent). Removed in join order, the parent left first and the later bulb's Leave never
arrived: on ZHA that happened on 3 of 4 back-to-back removes, with route failures for the stranded bulb, and a
5 s gap between removes didn't help. A stranded bulb stays on the old network, invisible to HA and deaf to the
next one, until power-up makes it announce; once it hung half-initialized until it found a new parent. A Z2M remove
that failed with "Delivery failed", on a bulb that had rejoined on its own, is likely the same. The rig now records the order the bulbs appear on a
network (journaled) and releases them in reverse; the next round trip took every Leave.

**ZHA groups.** A group of all three bulbs gets its light entity at once. A one-member group never gets one, so the
A60's `group_color` group isn't made on ZHA (Later: a second color bulb).

**A switched-off lamp looks like a stuck bulb.** Twice a lamp switched off by hand mid-move missed every join and
search; the rig names it as on no network. Check the lamp's switch before a Bluetooth reset.

**The first unattended lab run** took 34 min (the plan estimated 95): every move clean, 125 cases passed, 26
failed, and 12 actions passed whole, so their records now read `Profile | lab`. The failures, tracked in `TODO.md`
as the slice 15 follow-up:

| Cause | Cases |
|---|---|
| Group cases expect every member to take color temperature; the lab group holds the White bulb | `sets_while_off[group]`, `sets_after_a_soft_off[group]` (Hue, ZHA), `reads_while_off[group]` (ZHA) |
| Z2M `not_stored` on the white ambiance bulb, which had no `hue_native_control` in its options (since added; to be rerun) | 8 Z2M `set_attributes` cases on `light_ct` and `group` |
| A Hue `get_attributes` case calls `turn_on_for`, which Hue has no adapter for; it should skip | `reads_a_running_timer[light_dimmable]` |
| ZHA doesn't keep a setting made while the white ambiance bulb or the A60 is off | ZHA `sets_while_off[light_ct]`, `sets_hs_while_off`, `sets_xy_while_off` |
| Full brightness on power-up after a soft off | `sets_after_a_soft_off[light_ct]` (Hue, ZHA) |
| Single readings: the White bulb's dimmest level is 13 (case expects at most 8); a bulb still off 2 s after a set; the A60 at 53.1 after a halt (at most 50); its hue at 60 (134 to 158); a Z2M group at 3354 K (2650 to 2750) | `up_from_off_shows_the_dimmest[group]`, `lower_to_off`, `halts_brightness_and_hue[light_color]`, `cycles_down_the_wheel`, `keeps_and_reads_hs_while_off`, Z2M `reads_while_off[group]` |

**Hue → Z2M, the one direct move the A60 probe never tried, failed twice on 3 Nov, then passed.** Once a bulb
joined but Z2M's interview failed (`Delivery failed`), so it wasn't interviewed within the 120 s window; once the A60
joined nothing and needed a Bluetooth reset. Z2M logs at `warning`, so neither join left a trace. Since then a Z2M
join asks again after a failed interview (up to 3 times) and holds Z2M at `info` while the window is open, putting
its own level back after (journaled, so `--recover` does it after a crash). A run stopped by a move now still
reports and records the phases before it.

**The third bulb into Z2M kept failing (3 Nov, 4 of 5 moves).** Z2M's network map put the first two on one old
plug acting as their router, and the third through it failed; when the A60 "never joined", a Hue search adopted it
at once, which looked like a missed Leave. Z2M joins now open on the coordinator only, and a bulb from Hue
still missing 30 s after the last join, once the rest are in, is searched back, released alone and given one more
window (#174; plan: `2026-11-03-rig-z2m-join-route.md`). On the lab that afternoon, coordinator-only joins took all three bulbs in about 20 s, clean, every time. The A60's
Hue → Z2M move still failed: the retry spotted it and a search took it back at once, but released alone it still
didn't join. Hue → ZHA and ZHA → Z2M went 2 of 2, so the route, not the release order, looks like the fault; the
next try captures Z2M's log (`2026-11-03-rig-run-logs.md`). One run also saw Z2M stall for 8 minutes after the
joins, dropping off MQTT four times; a probe ruled out the log-level change as a reliable trigger.

**HomeKit Bridge** registers a three-part device identifier; the rig's IEEE lookups now accept any length. The
integration's Z2M lookups only see `mqtt` devices, whose identifiers are always pairs, so they were left alone.
