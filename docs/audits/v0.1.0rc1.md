# a518efe..4f709eb audit: 2026-11-04 (v0.1.0rc1)

Auditing `a518efe..4f709eb` (v0.0.1 to release/v0.1.0's head): 206 commits, 354 files, +45,784/−1,293. The shipped
code is `custom_components/device_side/` (97 changed files, about 6.6k lines, nearly all new since v0.0.1). The
scripts and workflows that gate a release and the tests were reviewed too. Six reviewers each read a slice in full
(core and actions; Hue, Shelly and Matter; ZHA with the shared ZCL modules; Zigbee2MQTT; release scripts and CI;
tests), and every Critical, High and recommended Medium was re-read against the code before it went in here.

**Verdict.** This is a sound codebase. Adapter contracts are uniform, failures are isolated per target, and the tests
use fake clocks throughout. It has **0 Critical, 3 High, 9 Medium, 12 Low**. The most important finding is H1: the
manifest still says `0.0.1`, and nothing stops a `v0.1.0` tag that disagrees with it. The other two Highs are on
failure paths: a Hue scene that partly failed reports success (H2), and a failed ZHA send drops a pending soft-off
restore (H3).

The lab session may still change adapter scopes and `experimental` flags after `4f709eb`. A fix pass covers those
commits before the RC is cut. At `4f709eb`, eight adapters carry `experimental=True`: Hue, ZHA and Z2M
`set_attributes` and `stop`, ZHA `lower_brightness` and Z2M `lower_hue`. That blocks `cut-release` but not an RC.

Ground truth: 1688 tests pass offline in 79 s; pre-commit (ruff, secrets, household check) is clean; no MAC, IEEE or IP
in the shipped tree looks real.

**H1**, `scripts/check_tag.py` `errors`. HA and HACS show the version from the manifest, so a tag that disagrees
with it ships a release that names itself wrongly, and no gate catches it.

```python
def manifest_error(repo: Path, version: Version) -> str | None:
    found = json.loads((repo / MANIFEST).read_text()).get("version")
    return None if found == name(version)[1:] else f"{MANIFEST} has version {found!r}, not {name(version)[1:]!r}"
```

**H2**, `integrations/hue/set_scene.py:80` `HueSetScene.execute`. A failed light reported as `sent` lets an
automation carry on over a device failure, which core would raise.

```python
if failed:
    detail = "error" if failed == len(writes) else "some_lights_failed"
    return self.result(target, Status.REJECTED, detail=detail)
return self.result(target, Status.SENT)
```

**H3**, `integrations/zha/fade.py:281` `start`. A send that fails must leave the restore marks as they were, or an
earlier soft off's restore is lost and the light comes back on near zero.

```python
kept = pending & outcome.starts.keys()
pending.difference_update(outcome.starts)

try:

    pending.update(kept)
```
