# Other brands: ExecuteIfOff writes and live reads on Zigbee lights

2026-11-24. Research for opening Zigbee2MQTT's `other` class (lights of brands with no family) to `set_attributes` and
`get_attributes` in Labs. Four parts, each researched separately against primary sources; claims carry their links in
the parts below, and anything a part couldn't confirm is marked unverified there.

## Synthesis

- **Spec.** The Options attribute (0x000F), its ExecuteIfOff bit and the OptionsMask/OptionsOverride command fields
  arrived in ZCL rev 7 (2017, with ZLO 1.0), not rev 6. In ZCL 8, Options is mandatory in Level Control for Lighting and
  in Color Control. Whether Zigbee 3.0, ZLO or ZLL certification requires them is unverified (spec PDFs not reachable).
  With ExecuteIfOff unset, a MoveTo to an off light is to be ignored: nothing stored, the light stays off (Part 1).
- **Older firmware rejects the fields, it doesn't misread them.** A pre-rev-7 bulb answers MALFORMED_COMMAND (Paul
  Neuhaus, Z2M #30603); zigbee-herdsman-converters opts some models out (Schneider NHPB/DIMMER/1, Ribag) (Part 1).
- **No reported departure among `other`'s vendors.** None found for Aqara, Innr, Ledvance/Osram, Lidl/Livarno, Müller
  Licht, Paulmann, Nanoleaf, EcoDim or Hornbach/flair, either way: absence of reports, not support. Innr RB 287 C is
  reported to honor ExecuteIfOff. One L&S Lighting MEC module (756200030, Z2M #33679) reports ON on a brightness write
  while off with the load staying off (ZHC's own write, not the override). The known departers, Sengled E11-G13 (jumps
  to full and comes on) and IKEA KAJPLATS (stores, comes on at its old level), are already outside `other` (Parts 2a, 2b).
- **No field evidence for the override on Z2M.** ZHC always sends optionsMask 0; Z2M exposes `execute_if_off` only as
  an Options-attribute write, which some bulbs reset on power loss or don't have (Osram, UNSUPPORTED_ATTRIBUTE, Z2M
  #6402). DeviceSide's per-command override is exercised only by DeviceSide's own probes and rig records (Parts 1, 2a).
- **Model quirks.** Innr sets `turnsOffAtBrightness1` on 92 definitions (level 1 reads as off). Tuya-inside Lidl lights
  use Tuya's converter, not standard color commands (Part 2a).
- **Reads.** No report of a Read Attributes changing a device's state. On Z2M one UNSUPPORTED_ATTRIBUTE fails the whole
  cluster read (herdsman `Endpoint.read`): Paulmann RGBW advertises XY yet can't read currentX/currentY (Z2M #33439),
  Müller Licht GU10 likewise (Z2M #12720). onTime is not required in herdsman's cluster table; colorMode and
  currentLevel are. Read timeouts follow mesh congestion (Part 3).

## Part 1: Spec and converter behavior (Options / ExecuteIfOff / OptionsMask / OptionsOverride)

Date: 2026-11-24. Sources pinned: zigbee-herdsman-converters (ZHC) `03b37655f`, zigbee-herdsman (ZH) `d6d2b39d2`, zha `c2011c470`, zigpy `8b7716ad0`.

Spec text source: ZCL **Revision 8** (Document 07-5123-08, Dec 2019), read from a third-party mirror, [etc.athom.com/zigbee_cluster_specification.pdf](https://etc.athom.com/zigbee_cluster_specification.pdf) (its cover says "Document 07-5123 Revision 8"). The CSA-hosted ZCL 6 PDF ([csa-iot.org/.../07-5123-06-zigbee-cluster-library-specification.pdf](https://csa-iot.org/wp-content/uploads/2019/12/07-5123-06-zigbee-cluster-library-specification.pdf)) returned HTTP 403 to my client, so **ZCL 6 and ZCL 7 text itself is unverified**; everything about them below comes from ZCL 8's own Document History and cluster Revision History tables. Section numbers/page refs are ZCL 8's.

### Summary

1. Options (0x000F), ExecuteIfOff and the OptionsMask/OptionsOverride command fields arrived in **ZCL rev 7 (Nov 2017)** with ZLO 1.0, not rev 6.
2. In ZCL 8 the attribute is **Optional in base Level Control, Mandatory in Level Control for Lighting and in Color Control**. The two command fields "SHALL both be present" in ZCL 8, with defaults (0, 0) for fields missing from legacy senders.
3. The spec says nothing about what a legacy *receiver* does with two extra bytes. In the field, **some pre-rev-7 devices reject them with MALFORMED_COMMAND** (Schneider NHPB/DIMMER/1, Paul Neuhaus lights), and ZHC has a per-model opt-out for them.
4. While off with ExecuteIfOff=0, a Move/MoveTo-without-OnOff is to be **ignored entirely** (level not stored). The spec does not describe a "stored but comes on" outcome; that is a non-conformance.
5. Z2M passes `optionsMask`/`optionsOverride` through its generic `command` converter unchanged. **ZHC itself only ever sends 0/0** and never a non-zero override; it uses the Options *attribute* write for ExecuteIfOff. DeviceSide's mask=1/override=1 has no precedent in ZHC.

### 1. Which ZCL revision introduced them

- ZCL Document History, rev 07 (Nov-2017), Chapter 3: "Level Control cluster State Change Table ... ZLO 1.0 changes to Level Control for Lighting ... CCB 1499 1584 1775 2085 2147 ..."; Chapter 5: "ZLO 1.0; **Options Attribute**; CCB 2085 2104 2124 2193 2230 2393". Rev 06 (14-Jan-2016) lists Chapter 5 as "ZLL 1.0 errata CCB 2028 2106" and no Options. ([ZCL 8 mirror](https://etc.athom.com/zigbee_cluster_specification.pdf), Document History)
- Level Control Revision History (3.10.1.1): "Rev 1 global mandatory ClusterRevision attribute added; **Rev 2 added Options attribute, state change table; ZLO 1.0; Base cluster (no change)**; CCB 2085 1775 2281 2147; Rev 3 CCB 2574 2616 ...".
- Color Control Revision History (5.2.1.1): "Rev 1 mandatory global ClusterRevision attribute added; CCB 2028. **Rev 2 added Options attribute**, CCB 2085 2104 2124 2230; ZLO 1.0. Rev 3 CCB 2501 2814 2839 2840 2843 2861".
- ClusterRevision itself became mandatory in ZCL 6 (Foundation, 2.3.x: "mandatory for all cluster instances ... conforming to ZCL revision 6 (ZCL6) and later"). So a rev-6 bulb that reports cluster revision 1 for these clusters has no Options. Inference: the cluster revision (>= 2) is the in-band way to detect support; not verified on real devices here.
- Revision 3 of both clusters carries CCB 2814 ("defaults for legacy devices" / "fields are mandatory because fields may follow", footnotes 52-53 and 90-111 of ZCL 8): the rule that the two fields are always present and what defaults a receiver applies to missing ones came **after** the fields were added.
- Cross-check against code: ZH marks the fields optional "due to likely missing fields with many devices" ([ZH cluster.ts L713-L724](https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/zspec/zcl/definition/cluster.ts#L713)), and zigpy's schema marks them optional (`"options_mask?"`, [zigpy general.py L1050-L1055](https://github.com/zigpy/zigpy/blob/8b7716ad0f17c05e48a6b4a3af554b4ea78ea858/zigpy/zcl/clusters/general.py#L1050-L1055)).

### 2. Mandatory or optional, rev 6/7/8; Zigbee 3.0 / ZLL

| Item | ZCL 6 | ZCL 7 | ZCL 8 (verified text) |
|---|---|---|---|
| Options attr in Level Control (0x0008, base) | absent (inferred, unverified) | present (added, unverified text) | Table 3-56: `0x000F Options map8 RW default 0, O` |
| Options attr in Level Control for Lighting | absent | unverified | Table 3-143: `Options base base **M**` |
| Options attr in Color Control | absent | unverified | Table 5.x (Color attrs): `0x000f Options map8 RW 0x00 **M**` |
| OptionsMask/OptionsOverride in commands | absent | unverified | "SHALL both be present" (3.10.2.3.1.2 and 5.2.2.3.3), defaults 0/0 "to interpret missing fields from legacy devices"; footnote: "CCB 2814 fields are mandatory because fields may follow" |

- ExecuteIfOff semantics, ZCL 8 3.10.2.2.8.1: "Command execution SHALL NOT continue beyond the Options processing if all of these criteria are true: the command is one of the 'without On/Off' commands: Move, Move to Level, Stop, or Step; the On/Off cluster exists on the same endpoint; the OnOff attribute is 0x00 (FALSE); the value of the ExecuteIfOff bit is 0." Color Control (Table 5.6, same text minus the first bullet) applies to all color commands, which cannot be "with On/Off".
- Temporary Options: "Each bit in the Options attribute SHALL determine the corresponding bit in the temporary Options bitmap, unless the OptionsMask field is present and has the corresponding bit set to 1, in which case the corresponding bit in the OptionsOverride field SHALL determine it." So mask=1/override=1 is the spec'd per-command way to force ExecuteIfOff=1 for one command, with no attribute write.
- Zigbee 3.0 / ZLO certification: **unverified**. The ZLO device spec (15-0014) was not retrievable (CSA 403, no mirror found). What the ZCL 8 text supports: Options is M in Level Control for Lighting and Color Control, and the revision histories tie its addition to "ZLO 1.0", so a ZLO-certified dimmable/CT/color light is expected to expose it. Whether a given certified product honors the *override fields* or the bit in practice is a device question; see section 5.
- ZLL (Zigbee Light Link 1.0): **unverified**. ZLL predates ZCL 7 (ZCL 6's Chapter 5 cites "ZLL 1.0 errata"), so ZLL-only bulbs are expected not to implement Options. Field evidence: Hue E14 and Tradfri GU10 WS accepted a write of the Color Control `options` attribute but ignored it ([ZHC #2253, sjorge's test comments](https://github.com/Koenkk/zigbee-herdsman-converters/issues/2253)); some Hue bulbs return UNSUPPORTED_ATTRIBUTE for the attribute ([ZHC #9426 comments](https://github.com/Koenkk/zigbee-herdsman-converters/pull/9426), [Z2M #27568](https://github.com/Koenkk/zigbee2mqtt/issues/27568), reverted in [ZHC #9442](https://github.com/Koenkk/zigbee-herdsman-converters/pull/9442)). The same issue reports others (LCA008, LTG005) read back `options` fine.

### 3. Trailing fields a legacy device does not know

- The spec text I could read **does not state** whether a receiver ignores or rejects extra payload bytes. It only (a) tells *receivers* to default missing fields for legacy *senders* (CCB 2814 footnotes), and (b) defines MALFORMED_COMMAND 0x80 as "The command appears to contain the wrong fields, as detected either by the presence of one or more invalid field entries or by there being missing fields. Command not carried out. Implementer has discretion as to whether to return this error or INVALID_FIELD." (ZCL 8 Table 2-12). A pre-rev-7 device that validates length strictly is therefore spec-defensible in rejecting.
- Field evidence that it does reject, and does not store the value:
  - **Paul Neuhaus** (NLG-CCT, firmware ID 1001-0007, dated 2015-08-21; JZ-CT-Z01) after Z2M 2.7.2: log "Failure default response ... clusterID=8 cmdId=4 status=MALFORMED_COMMAND" on moveToLevelWithOnOff; on/off still works, brightness and CCT do not ([Z2M #30603](https://github.com/Koenkk/zigbee2mqtt/issues/30603), [Z2M #30705](https://github.com/Koenkk/zigbee2mqtt/issues/30705)). A reporter attributes the change to herdsman 8.0.0 starting to send the two bytes (reporter's analysis; **unverified** by me). Fixed per model with `meta: {omitOptionalLevelAndColorParams: true}` ([ZHC #12221](https://github.com/Koenkk/zigbee-herdsman-converters/pull/12221), [#12668](https://github.com/Koenkk/zigbee-herdsman-converters/pull/12668); flag at [paul_neuhaus.ts L56](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/devices/paul_neuhaus.ts#L56)). #12221 says the fix "removes the extra options in the payload"; #12668 was needed because color/CT still failed, so omitting only some commands' bytes was not enough (cause not stated; unverified).
  - **Schneider Electric NHPB/DIMMER/1** (WDE002386, firmware 001.005.000 R): reporter, citing the vendor's spec, says it "rejects frames containing them ... may return MALFORMED_COMMAND or silently drop commands" ([Z2M #30701](https://github.com/Koenkk/zigbee2mqtt/issues/30701); the reporter's wording is hedged). ZH maintainer's position: "We cannot remove them (even if zero), as that would go against the proper spec ... Handling devices that don't follow the spec should always go in ZHC" ([ZH #1617](https://github.com/Koenkk/zigbee-herdsman/pull/1617)). Resolved by letting ZH omit parameters that carry a MINIMUM_REMAINING_BUFFER_BYTES condition ([ZH #1619](https://github.com/Koenkk/zigbee-herdsman/pull/1619), commit [2670e25](https://github.com/Koenkk/zigbee-herdsman/commit/2670e25c1badad038371dc42e1287938c49dcd46); code at [zclFrame.ts L98-L122](https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/zspec/zcl/zclFrame.ts#L98)) plus the ZHC flag ([ZHC #11340](https://github.com/Koenkk/zigbee-herdsman-converters/pull/11340); [schneider_electric.ts L2790](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/devices/schneider_electric.ts#L2790)), and **Ribag Air O** ([ZHC #12865](https://github.com/Koenkk/zigbee-herdsman-converters/pull/12865); [ribag.ts L11](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/devices/ribag.ts#L11)) uses the same flag (PR says only the pendant dates "to around 2016").
  - Flag definition: "Omit optional optionsMask/optionsOverride parameters for devices with strict ZCL v1 compliance" ([ZHC types.ts L190-L194](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/lib/types.ts#L190)). Only 3 vendors/families set it (Paul Neuhaus x10 definitions, Schneider x1, Ribag x1) at the pinned commit.
- The converse: ZHC sends the two zero bytes on essentially every Z2M light command by default (below), and only these few models are reported broken. So most legacy-era bulbs that are still in service tolerate the trailing bytes. I found no survey of how many; treat "ignore" as the common case and "reject" as a known minority. **Unverified** beyond these reports.
- Behavioral consequence for DeviceSide: a rejected write is detectable (Default Response status 0x80 or no reaction), a silent drop is not. Sending the bytes to a pre-rev-7 device has precedent for failure; DeviceSide can gate on cluster revision (>= 2 on both clusters) or on the `options` attribute being readable before sending override fields (both are suggestions, not tested).

### 4. What a light does with Move/MoveTo while off when ExecuteIfOff is not honored

- Level Control for Lighting state change table (ZCL 8 3.19.4, Table 3-146): EiO=0, OnOff=0, "Move to level MID over 2 sec" gives CurrentLevel "same", OnOff 0, "Off, stays off". EiO=1, same command gives CurrentLevel MID, OnOff 0, "stays off". "Move with On/Off" turns on and applies level in both cases.
- Color Control generic usage (5.2.2.3.1): "If one of these commands is received while the device is in its off state, i.e., the OnOff attribute of the on/off cluster is equal to 0x00, the command SHALL be ignored." (This is the default; the Options processing in 5.2.2.2.1.10 / 5.2.2.3.3 is what changes it.)
- So when ExecuteIfOff is not honored, the **conformant outcome is "ignored, nothing stored, stays off"**. The two outcomes already seen in DeviceSide's own devices, Sengled E11-G13 turning on at full, and IKEA KAJPLATS storing the level but waking at its old one, are both **outside the spec table** (the Sengled one turns the light on from a command that has no OnOff effect; the IKEA one stores state the spec says should be ignored then does not use it). No further published reports of either behavior were looked for here (that is Part 2+ territory).
- Z2M's own non-OnOff path shares the same expectation: "{brightness: 70, state: null}" sends MoveToLevel, and a user states "If the light turns on with state null ... the light is not following Zigbee specification. Execute if off: ON: light should accept MoveToLevel; OFF: light should ignore MoveToLevel" ([Z2M #27743](https://github.com/Koenkk/zigbee2mqtt/issues/27743), the commenter's reading, consistent with the ZCL table above). Same thread: "Since the last update ... the lamp switches on" for a report on an unnamed lamp; **no model named**.

### 5. How ZHC / Z2M send these

**Generic `command` passthrough.** `toZigbee.command` (key `command`) calls `entity.command(value.cluster, value.command, value.payload ?? {}, options)` with the payload object unmodified ([toZigbee.ts L240-L247](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/converters/toZigbee.ts#L240)); it is prepended to every device's converter list ([index.ts L432](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/index.ts#L432)). ZH serializes whatever named fields are present: fields with a `MINIMUM_REMAINING_BUFFER_BYTES` condition (the Options fields on moveToLevel, move, step, stop and the color commands) are written if given, and silently skipped if absent; any other missing field throws ([zclFrame.ts L98-L122](https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/zspec/zcl/zclFrame.ts#L98); definitions [cluster.ts L713-L724](https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/zspec/zcl/definition/cluster.ts#L713), color-control commands from [L2242](https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/zspec/zcl/definition/cluster.ts#L2242)). So `{"command": {"cluster": "genLevelCtrl", "command": "moveToLevel", "payload": {"level": N, "transtime": 4, "optionsMask": 1, "optionsOverride": 1}}}` reaches the wire as-is (by reading the code; I did not run it). The bit enums exist in ZH: `LevelOptionsMask.ExecuteIfOff = 0x01`, `CCColorOptionsMask.ExecuteIfOff = 0x01` ([datatypes.ts L669-L670, L861-L862](https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/zspec/zcl/definition/datatypes.ts#L669)).

**Normal light converters always send zeros, never an override.** `light_color`, `light_colortemp`, `light_onoff_brightness`, brightness move/step etc. build `optionalParams = omit ? null : {optionsMask: 0, optionsOverride: 0}` ([light_color L59-L69](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/converters/toZigbee.ts#L68), [light_colortemp L175-L182](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/converters/toZigbee.ts#L181), [light_onoff_brightness L1252-L1261](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/converters/toZigbee.ts#L1260)). `rg` over ZHC and ZH `src` for a non-zero `optionsMask`/`optionsOverride` finds **none**. (Several device files also hand-write `optionsMask: 0, optionsOverride: 0`, e.g. [ikea.ts L1113, L1124](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/lib/ikea.ts#L1113).)

**Z2M's "no state change" path.** `brightness` with `state: null` uses `moveToLevel` instead of `moveToLevelWithOnOff`; with `state` unset it infers on/off and uses `moveToLevelWithOnOff` "so that'd break backwards compatibility. To keep the state, the user has to explicitly set it to null" ([toZigbee.ts L1284-L1292, L1406](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/converters/toZigbee.ts#L1284)). It sends mask 0/override 0 so it relies on the device's own Options attribute.

**ExecuteIfOff is handled as an attribute write, per device, user-driven.**
- `light_color_options` writes `lightingColorCtrl.options = execute_if_off ? 1 : 0` and reads it back ([L378-L390](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/converters/toZigbee.ts#L378)); `level_config` writes `genLevelCtrl.options` the same way ([L856-L863](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/converters/toZigbee.ts#L856)), whose in-code comment states bit 0: "when 0, Move commands are ignored if the device is off".
- `m.light()` always adds `tz.light_color_options` when color or CT is present, and the level config only when `levelConfig` is passed ([modernExtend.ts L1347-L1356](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/lib/modernExtend.ts#L1347)). The expose reads "Controls whether color and color temperature can be set while light is off" ([exposes.ts L1136](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/lib/exposes.ts#L1136)).
- Per-model: `levelConfig.features` includes `execute_if_off` for IKEA by default ([ikea.ts L86-L88](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/lib/ikea.ts#L86)), Enbrighten (2), Vesternet, Slacky DIY (2), Leviton, Lumi (2), Namron, Ubisys.
- The Hue-wide enablement was **added then reverted** (ZHC [#9426](https://github.com/Koenkk/zigbee-herdsman-converters/pull/9426) -> [#9442](https://github.com/Koenkk/zigbee-herdsman-converters/pull/9442)) because some Hue bulbs return UNSUPPORTED_ATTRIBUTE; ZHC maintainers' reasoning: "I'm not sure how to filter which do and do not support this" ([Z2M #27568](https://github.com/Koenkk/zigbee2mqtt/issues/27568)). Users can still write it over MQTT.
- **The attribute is volatile on some devices.** IKEA: "some other information is lost like color_options.execute_if_off. We also restore these" on deviceAnnounce ([ikea.ts L36-L67](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/lib/ikea.ts#L36)); Leviton DG3HL restores it after a mains cycle detected via TSN 1 ([leviton.ts L26-L35](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/devices/leviton.ts#L26)). FLOALT firmware upgrade flipped the bit to 0 ([ZHC #2253](https://github.com/Koenkk/zigbee-herdsman-converters/issues/2253)). Per-command override sidesteps this; the attribute path needs restore logic. (These are code comments and a reporter's note, not measured.)
- **No ZHC per-model workaround for "off + Move" quirks beyond these.** The closest are `moveToLevelWithOnOffDisable` (5 Tuya definitions) and `turnsOffAtBrightness1`, which concern on/off transitions rather than ExecuteIfOff. I did not find a ZHC entry for Sengled E11-G13 handling off-staging.

### 6. ZHA / zigpy comparison (for context)

- zigpy schemas make `options_mask`/`options_override` optional, and ZHA never passes them. ZHA instead **reads the Color Control `options` attribute** and checks the ExecuteIfOff bit: `_execute_if_off_supported = Execute_if_off in _color_options` ([ZHA light/__init__.py L313-L322](https://github.com/zigpy/zha/blob/c2011c4702458181ebb52cc728051e27d9bd0816/zha/application/platforms/light/__init__.py#L313-L322)); when true it sends color commands *before* turning on, otherwise it turns on first then sets color (the "enhanced transition from off" workaround) ([L393-L396, L540, L601](https://github.com/zigpy/zha/blob/c2011c4702458181ebb52cc728051e27d9bd0816/zha/application/platforms/light/__init__.py#L540)); for groups it requires every member to have the bit ([L1394-L1426](https://github.com/zigpy/zha/blob/c2011c4702458181ebb52cc728051e27d9bd0816/zha/application/platforms/light/__init__.py#L1394-L1426)). Color attributes only, not level: ZHA still turns on with `move_to_level_with_on_off`.
- Z2M asked for the same ("check if the bulb has ExecuteIfOff, then split the MQTT payload") and it is an open request ([Z2M #22653](https://github.com/Koenkk/zigbee2mqtt/issues/22653), whose own workaround is to write `options = 1` on both genLevelCtrl and lightingColorCtrl from the dev console).

### 7. Implications for the "other brands" Labs tier (judgment, not sourced fact)

- The override fields are spec-correct for rev-7+ devices but I found **no field evidence at all** of devices tolerating mask=1/override=1 via Z2M: ZHC never sends non-zero values, so no Z2M test base exists for it. ZHA users effectively exercise the *attribute* path, not the override. Treat "override honored" as a per-device finding, to be probed.
- The two extra bytes alone are risky on pre-rev-7 firmware (Paul Neuhaus, Schneider, Ribag). Because Z2M's default already sends them, DeviceSide adds no *new* exposure for devices Z2M controls normally, but for a set_attributes-only call a failure would otherwise surface as no change, not as an error. A cluster-revision check (>= 2) or readable `options` attribute before sending would filter these (suggestion; not tested).
- A device that honors neither the attribute nor the override may do one of three non-conformant things already seen: turn on and jump to full (Sengled E11-G13), accept and store but wake at the old value (IKEA KAJPLATS, Matter), or (per spec) ignore. Only "ignore" is safe to offer; the other two are the hazard classes the Labs gate must exclude.
- Reads: `onTime` and `currentLevel`/`colorMode` reads need no Options support. `colorMode` (0x0008) is M in Color Control; `currentLevel` is M in Level Control; `onTime` is an On/Off attribute (not re-checked here; not covered by this part).

### Other findings that bear on the DeviceSide decision

1. **Z2M's `execute_if_off` and `color_options` are first-class only for IKEA/Hue-class devices**, so Z2M gives no cross-vendor corpus of "this bulb honors ExecuteIfOff". The corpus has to come from DeviceSide's own probe (read Options 0x000F on Level Control and Color Control, then write-while-off, then read currentLevel/colorMode and onOff). Recommended probe order for "other" brands: read `lightingColorCtrl.options` and `genLevelCtrl.options`; if UNSUPPORTED_ATTRIBUTE, refuse staging (the Lightify precedent, [#6402](https://github.com/Koenkk/zigbee2mqtt/issues/6402)).
2. **Per-model quirks that would silently break staging even when Options is honored**: Innr level 1 = off ([toZigbee.ts L1375](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/converters/toZigbee.ts#L1375)); Tuya-inside Lidl bulbs do not use standard color commands ([#33627](https://github.com/Koenkk/zigbee2mqtt/issues/33627)).
3. **Z2M's own scene fallback**: where bulbs lack ExecuteIfOff, the community stages color by scene add/recall ("abusing scenes", [ZHC#2253](https://github.com/Koenkk/zigbee-herdsman-converters/issues/2253), written about IKEA FLOALT; also states that firmware update reset ExecuteIfOff 1 to 0 and broke staging, so the bit can change under a firmware update: re-read it, do not cache it). That is relevant to the "verified facts stand across firmware" tenet: for ExecuteIfOff, firmware changes are documented to flip it.
4. **ZHC tracker** [#11893](https://github.com/Koenkk/zigbee-herdsman-converters/issues/11893) (open) lists "generated definition omits useful attributes (onOffTransition, executeIfOff...)": i.e. the maintainers' own view is that ZHC does not yet expose ExecuteIfOff for most generated definitions.

### What ZHA does with it (for the get path)

ZHA reads the colour cluster Options attribute and, if bit 0 is set, sends colour commands *before* turning on; if clear, it sends them *after* turning on ([zha light L321-322](https://github.com/zigpy/zha/blob/c2011c4702458181ebb52cc728051e27d9bd0816/zha/application/platforms/light/__init__.py#L321), [L540-546](https://github.com/zigpy/zha/blob/c2011c4702458181ebb52cc728051e27d9bd0816/zha/application/platforms/light/__init__.py#L540), [L601-603](https://github.com/zigpy/zha/blob/c2011c4702458181ebb52cc728051e27d9bd0816/zha/application/platforms/light/__init__.py#L601)). It trusts the device-reported bit and never verifies behavior. For groups it requires every member to report the bit ([L1413-1426](https://github.com/zigpy/zha/blob/c2011c4702458181ebb52cc728051e27d9bd0816/zha/application/platforms/light/__init__.py#L1413)). ZHA therefore has no per-model departure list either (no `ExecuteIfOff` hits in zigpy/zha-device-handlers or zigpy code search; only zigpy/zha and its HA test files reference `execute_if_off`). A bulb that reports the bit as set but ignores it would be mishandled by ZHA the same way; none reported.

## Part 3: reads (onTime, currentLevel, colorMode and color attributes) on non-Hue Zigbee bulbs

Researched 2026-11-24. Code links are pinned to these commits: zigbee-herdsman `d6d2b39d20`, zigbee-herdsman-converters (ZHC) `03b37655f5`, zigpy `8b7716ad0f`, zigpy/zha `c2011c4702`, connectedhomeip `a9eaba9e42`. Issue text is quoted from the reporter.

### Bottom line

1. **No report found of a plain attribute read turning a light on, resetting it, rejoining it or crashing its firmware.** Searched Z2M, ZHC, herdsman, ZHA (zigpy/zha), zigpy and HA core issues with several phrasings (about 30 queries; GitHub search is keyword-based and weak, so this is "not found", not "does not exist"). The nearest item is HA core #76893 (below), which is a correlation with an unknown cause, not evidence. Reads are specified as side-effect free; I found no counter-report.
2. **The real read failure is whole-read failure through Z2M.** One unsupported attribute in a multi-attribute `read` makes herdsman throw, and Z2M discards the other attributes that were returned. ZHA/zigpy do the opposite: per-attribute failures, the rest returned.
3. **Timeouts are 10 s per read by default and surface as errors; stale or odd values are a device-firmware problem** (a Tuya TS0505B reports currentLevel 0 to 3 while on, or 1 after off).
4. **onTime is the least-exercised read.** Neither Z2M's standard light `/get` nor ZHA's light poll reads it; only a few Tuya/eWeLink converters do. It is optional in herdsman's cluster table. (ZCL spec text: unverified, see Mandatory attributes.)
5. **`colorCapabilities` can lie.** A Paulmann RGBW advertises XY (`colorCapabilities = 31`) but returns UNSUPPORTED_ATTRIBUTE for currentX/currentY. "Read only the attributes of the light's own color modes" is therefore not enough on its own; read per attribute and tolerate a miss.

### 1. How a read's error surfaces through Z2M (zigbee-herdsman)

- `Endpoint.read()` builds a ZCL Read Attributes frame and calls `zclCommand(..., checkStatus = true)`: [endpoint.ts L563-L602](https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/controller/model/endpoint.ts#L563-L602). Note the in-code `// TODO: handle \`attr.required !== true\` => should not throw` at L579.
- `zclCommand` calls `checkStatus(resultFrame.payload)` on the response; `checkStatus` maps every record to its status and throws `Zcl.StatusError` for the first non-SUCCESS one: [endpoint.ts L455-L459](https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/controller/model/endpoint.ts#L455-L459), [L1196-L1203](https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/controller/model/endpoint.ts#L1196-L1203). So **a read of N attributes where the device answers UNSUPPORTED_ATTRIBUTE for one throws, and the N-1 good values are never returned to the caller.** (Z2M may still see them as a `readResponse` message on the event path; the reporter in #33439 says state never got `colorMode`/`colorTemperature`.)
- Later code skips non-SUCCESS records "per ZCL spec" when converting a response ([zclFrameConverter.ts L27-L31](https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/controller/helpers/zclFrameConverter.ts#L27-L31)), but that is downstream of the throw for `Endpoint.read`.
- Default timeout is 10000 ms, `disableRecovery` false: [endpoint.ts L1013-L1030](https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/controller/model/endpoint.ts#L1013-L1030). A timeout rejects with the adapter's text, e.g. `... timed out after 10000ms` (log in Z2M #32557 below). A dead or sleeping device is otherwise an error like `Delivery failed for '2965'` ([#33167](https://github.com/Koenkk/zigbee2mqtt/issues/33167)).
- Sleepy end devices: requests go through a per-device pending-request queue when `device.pendingRequestTimeout` is non-zero ([endpoint.ts L400-L450](https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/controller/model/endpoint.ts#L400-L450)). Mains lights are routers, so this does not apply to the target class.

#### What Z2M/ZHC read on `/get`

- `light` state/brightness get: `genLevelCtrl.currentLevel` ([toZigbee.ts L569-L571](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/converters/toZigbee.ts#L569-L571)); on/off get: `genOnOff.onOff` only ([L56](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/converters/toZigbee.ts#L56)).
- Color get: `lightingColorCtrl` read of `readColorAttributes(...)` ([toZigbee.ts L171-L173, L1183-L1185, L1484-L1486](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/converters/toZigbee.ts#L171-L173)). `readColorAttributes` always adds `colorMode`, `currentX`, `currentY` (unless the get payload names only hue/saturation), and adds `currentHue`/`enhancedCurrentHue` + `currentSaturation` only when the definition says `supportsHueAndSaturation`/`supportsEnhancedHue` ([light.ts L16-L54](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/lib/light.ts#L16-L54)). Its comment: "Not all bulbs support the same features, we need to take care we read what is supported. ... e.g. IKEA Tådfri LED1624G9 only supports XY (zigbee-herdsman-converters#1340)". The capability knowledge is hand-curated per device definition, not read from `colorCapabilities`.
- Color temperature get: `["colorMode", "colorTemperature"]` ([toZigbee.ts L211-L213](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/converters/toZigbee.ts#L211-L213)).
- **onTime is not part of any standard light get.** ZHC reads `genOnOff.onTime` only in `src/lib/tuya.ts` ([L3409](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/lib/tuya.ts#L3409), a Tuya countdown) and `src/devices/ewelink.ts` ([L87](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/devices/ewelink.ts#L87)); it configures onTime reporting in `reporting.ts` ([L79-L80](https://github.com/Koenkk/zigbee-herdsman-converters/blob/03b37655f540668d94975c47550f249fc0d16e26/src/lib/reporting.ts#L79-L80)). So no mainstream bridge exercises an `onTime` read on bulbs, and there is little field evidence either way.

### 2. UNSUPPORTED_ATTRIBUTE and whole-read failure: real reports

- **Z2M #33439 (open), Paulmann RGBW "924.70", swBuildId PIIC413, Z2M 2.14.2 / herdsman 10.10.0** ([issue](https://github.com/Koenkk/zigbee2mqtt/issues/33439)). Reporter's table: `colorMode` 2, `currentHue` 14, `currentSaturation` 250, `colorTemperature` 370, `colorCapabilities` 31, `currentX`/`currentY` **UNSUPPORTED_ATTRIBUTE**, `enhancedCurrentHue` "fails". "`colorCapabilities = 31` advertises XY, but X/Y cannot be read." Result: "every `get color` / `get color_temp` fails completely" with `lightingColorCtrl.read(["colorMode","currentX","currentY","currentHue","currentSaturation","colorTemperature"]) failed (Status 'UNSUPPORTED_ATTRIBUTE')`. Consequence in HA: `color_mode: unknown`, brightness hidden while on. Xy *commands* work on this bulb ("the light visibly turned red, then blue"). He adds: "Before switching to Zigbee2MQTT, ZHA exposed these lights as `supported_color_modes: ["color_temp", "xy"]`... ZHA presumably tolerates unsupported attributes one by one" (his inference; confirmed from code below).
- **Z2M #12720 (closed, stale), Müller Licht GU10 45318/45327** ([issue](https://github.com/Koenkk/zigbee2mqtt/issues/12720)): `get color` and `get color_temp` both fail with `Status 'UNSUPPORTED_ATTRIBUTE'` on a read of `["colorMode","currentX","currentY","enhancedCurrentHue","currentSaturation","colorTemperature"]`; "The startup temperature, brightness and on/off state work fine." Maintainer: "`(Status 'UNSUPPORTED_ATTRIBUTE')'` indicates this it not supported by these bulbs." Which of the six the bulb lacks was not established (unverified).
- Related search hits where a bulb exposes color attributes it does not have (titles only, bodies not read, so unverified as read failures): Z2M [#23462 Sengled Z01-A19NAE26 "exposes invalid capabilities (color_xy)"](https://github.com/Koenkk/zigbee2mqtt/issues/23462), [#23880 Aqara T1M "Color (X/Y) & Color (HS) not working"](https://github.com/Koenkk/zigbee2mqtt/issues/23880), [#20528 "UNSUPPORTED_ATTRIBUTE with unsupported device"](https://github.com/Koenkk/zigbee2mqtt/issues/20528).
- ZHC's own comment (light.ts L21-L28 above) cites the IKEA LED1624G9 (XY only) as the origin of the hue/saturation gating.

#### How ZHA/zigpy behave instead (tolerant)

- `Cluster.read_attributes` returns `(success, failure)`: per-attribute statuses go to `failure[attr] = status`, successes to `success`; reads are split into chunks of `MAX_READ_ATTRIBUTES_PER_REQ` and attributes omitted from a response or `INSUFFICIENT_SPACE` are re-read one at a time: [zigpy/zcl/__init__.py L1295-L1424](https://github.com/zigpy/zigpy/blob/8b7716ad0f17c05e48a6b4a3af554b4ea78ea858/zigpy/zcl/__init__.py#L1295-L1424), [L1426-L1530](https://github.com/zigpy/zigpy/blob/8b7716ad0f17c05e48a6b4a3af554b4ea78ea858/zigpy/zcl/__init__.py#L1426-L1530). A device-level failure (timeout, delivery failure) still raises; a single-status response ("all reads failed") fills `failure` for every attribute ([L1441-L1446](https://github.com/zigpy/zigpy/blob/8b7716ad0f17c05e48a6b4a3af554b4ea78ea858/zigpy/zcl/__init__.py#L1441-L1446)). With `allow_cache`, a previously-learned unsupported attribute is answered from the cache as UNSUPPORTED_ATTRIBUTE without a radio request ([L1343-L1357](https://github.com/zigpy/zigpy/blob/8b7716ad0f17c05e48a6b4a3af554b4ea78ea858/zigpy/zcl/__init__.py#L1343-L1357)).
- ZHA's light poll (`async_update`) reads `on_off`, then `current_level`, then `color_mode, current_x, current_y` (+ `color_temperature` when supported, + `color_loop_active`) as three separate `safe_read`s; it **never reads onTime**: [zha light/__init__.py L1198-L1297](https://github.com/zigpy/zha/blob/c2011c4702458181ebb52cc728051e27d9bd0816/zha/application/platforms/light/__init__.py#L1198-L1297). It skips polling while a transition is under way and when the device is not `available`.
- `safe_read` swallows every exception and returns `{}`: "Rather have an entity that exists, but is in a maybe wrong state, than no entity" ([zha/application/helpers.py L79-L101](https://github.com/zigpy/zha/blob/c2011c4702458181ebb52cc728051e27d9bd0816/zha/application/helpers.py#L79-L101)). So in ZHA a timeout is silent and shows up as stale state, not as an error.

(attempt 1/2 ... timed out after 10000ms)"). That issue was closed by the reporter as user error ("one of their kids turned off one of the switches"), so it is **not** evidence of a bulb freezing; it is cited only for the timeout shape.
- [#32523](https://github.com/Koenkk/zigbee2mqtt/issues/32523) (closed): after Z2M 2.12.1 on a Z-Stack adapter, "Several devices report ZCL command timeouts: `Timeout after 10000ms`" including "Zigbee lights", "Repeated 'Refresh' or 'Get state' requests eventually wake the device up", and others add "The log is flooded with 'failed to ping' warnings ... mostly IKEA devices". This is network-level/coordinator-side loss and timeouts on routers under a request load; I did not establish a root cause (unverified). It shows that on a congested mesh a read simply times out; it does not show a read changing device state.
- [#33167](https://github.com/Koenkk/zigbee2mqtt/issues/33167) (Gledopto, open): "Failed to read state of 'Esstisch5' after reconnect (... lightingColorCtrl.read(["colorMode","colorTemperature"] ... failed (Delivery failed for '2965'.))" while the bulbs repeatedly leave the network. ### 5. Does a read ever change device state? (the crucial question)

- **Direct evidence for: none found.** I found no issue in which a Read Attributes request (onOff, currentLevel, colorMode, color attributes, onTime, or availability `zclVersion`) turned a light on, changed its level/color, reset it, made it rejoin or crashed it.
- **Closest item (weak, cause unknown): HA core #76893, "Since 2022.07 OSRAM Zigbee Lights are blinking after power on"** ([issue](https://github.com/home-assistant/core/issues/76893)): 7 OSRAM PAR16 50 TW on a Tasmota ZBBridge; "they start blinking randomly every 5 - 15 seconds (short off, then on again)", "When dimming or changing brightness or switching off (via zigbee) it turns again on to 100% bridghtness after next blink interval"; "downgrading to 2022.06 all problems are gone". The ZHA maintainer's reading of the logs: "I don't see the lights being commanded to blink. But I do see the `0xD455` device to joining/re-joining multiple time in sequence." The reporter bisected to the ZHA component (replacing `homeassistant/components/zha/` with 2022.6.7 files fixed it) and speculated "They restart because they receive a message they don't understand" (his words, a hypothesis tied to the new color_mode feature). The issue was closed "Fixed in 2022.9" with no linked PR or stated cause. **Unverified**: I could not tie it to a specific read. If real, it would be a bulb rebooting on an unsupported/odd request rather than a state-changing read; it predates the current ZHA rewrite.
- **Why a read should be inert:** a Read Attributes is a global (non-cluster-specific) foundation command; cluster commands (MoveToLevel etc.) are what change state. (Spec text not fetched: **unverified** against the ZCL PDF; herdsman's global/cluster frame-type split is visible at [endpoint.ts L1172-L1174](https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/controller/model/endpoint.ts#L1172-L1174).) The only state-sensitive read I found is the interaction with the *bridge*, not the bulb: after a read of an attribute the device doesn't have, Z2M (not the device) fails the whole operation.
- **Request flooding:** I found no report of a bulb crashing from read volume, only network/coordinator congestion producing timeouts (#32523 above; Z2M #32837 "whole network dies with SRSP - AF - dataRequest after 6000ms" on a CC2652P7 is a coordinator problem, title only read). Both ZHA's poll (3 reads per poll, gated on `allow_polling`) and Z2M's get (1 to 2 reads) are small; DeviceSide's get is 3 to 4 reads of up to 6 attributes, comparable.

### 6. Mandatory attributes

- **colorMode (lightingColorCtrl 0x0008):** herdsman marks it `required: true` ([cluster.ts L3802](https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/zspec/zcl/definition/cluster.ts#L3802)), as are `colorCapabilities` (L3863), `options` (0x000F) and `enhancedColorMode` (L3851). Mandatory in the Matter ColorControl cluster too (all features), see [Matter ColorControl.xml L314](https://github.com/project-chip/connectedhomeip/blob/a9eaba9e422312967483d9559b3e728bd160a175/data_model/1.5/clusters/ColorControl.xml#L314). The CSA ZCL spec text itself: **unverified** (not fetched); herdsman's flags are derived from it.
- **Conditional color attributes:** herdsman's own comments: currentHue "`required: true` only if bit 0 of colorCapabilities attribute is 1" ([L3781](https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/zspec/zcl/definition/cluster.ts#L3781)); currentX/currentY only if bit 3 ([L3786](https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/zspec/zcl/definition/cluster.ts#L3786)); colorTemperature only if bit 4. The Paulmann bulb violates its own advertised capability (bit 3 set, X/Y unreadable), so real devices break the conditional rule.
- **currentLevel (genLevelCtrl 0x0000):** `required: true` ([cluster.ts L2209](https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/zspec/zcl/definition/cluster.ts#L2209)).
- **onTime (genOnOff 0x4001): not required in herdsman** (no `required` flag, default 0, writable: [cluster.ts L630](https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/zspec/zcl/definition/cluster.ts#L630)); herdsman does flag `onOff` itself required. **In Matter, OnTime is mandatory only with the Lighting (LT) feature** ([Matter OnOff.xml L153-L156](https://github.com/project-chip/connectedhomeip/blob/a9eaba9e422312967483d9559b3e728bd160a175/data_model/1.5/clusters/OnOff.xml#L153-L156), same for GlobalSceneControl, OffWaitTime, StartUpOnOff). For Zigbee: the ZCL spec text and the Zigbee 3.0 device-spec requirements for Dimmable/Color lights are **unverified**; my recollection is that ZCL lists OnTime/OffWaitTime/GlobalSceneControl as optional on the On/Off cluster and that lighting device specs require them, but I did not confirm either from a primary source. Treat onTime as "usually present on lighting devices, not guaranteed", especially on non-certified bulbs. In the data I saw, `onTime` is absent from the Z2M `database.db` cluster attribute dumps quoted in #33439 and #32557 (those list only attributes Z2M itself read, so this is not evidence of absence).

### 7. Implications for DeviceSide (for the recommender, not a decision)

- A bundled read through Z2M (`/get` or a raw `read`) fails entirely on one bad attribute; **read each attribute in its own request** (or fall back to per-attribute reads on UNSUPPORTED_ATTRIBUTE) and record a miss as "absent", never as a failed get. ZHA/zigpy already isolate per attribute.
- **Do not trust `colorCapabilities` as a license to read X/Y**: #33439 is a counter-example. A color read that returns `colorMode` plus whichever of hue/sat/xy/colorTemperature the device answers is the safe shape.
- **onTime read is low-risk for state but unproven**: expect UNSUPPORTED_ATTRIBUTE on some bulbs, treat as "not applicable", and don't build on it for brands where nobody has read it.
- `currentLevel` is unreliable while OFF (0 to 3 on TS0505B) and can glitch while ON; the existing "only when on" rule is justified, but a Labs gate should still treat it as advisory.
- Reads time out at 10 s through Z2M; a get across several attributes on a weak router can take tens of seconds. ZHA hides timeouts (returns `{}`).
- The set path matters far more than the read path: the only documented bulbs that move on write-while-off (Sengled E11-G13, IKEA KAJPLATS) are from the write side (Part 1/2), not from reads.
