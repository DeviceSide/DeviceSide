## 1. Wire format (write)

Converter `sonoffExtend.inchingControlSet` (sonoff.ts L2686-L2775).

Transport: ZCL cluster-specific command, cluster 0xFC11 (custom cluster `customClusterEwelink`, L2267-L2320),
command name `protocolData`, command id 0x01, one parameter `data` = LIST_UINT8 (raw bytes, no length prefix
added by ZCL beyond the buffalo list encoding) (L2315). Sent with `manufacturerCode:
Zcl.ManufacturerCode.SHENZHEN_COOLKIT_TECHNOLOGY_CO_LTD` (L2755-L2759), which is 0x1286 (herdsman
`manufacturerCode.ts` L556,
https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/zspec/zcl/definition/manufacturerCode.ts#L556).
Frame: client-to-server, manufacturer-specific bit set, default response NOT disabled (see 2).
The custom cluster has no cluster-level manufacturer code; the code is passed per command only.

Payload bytes (11 bytes), as built in L2728-L2754:

| idx | value | meaning |
|---|---|---|
| 0 | 0x01 | Cmd |
| 1 | 0x17 | SubCmd (inching) |
| 2 | 0x07 | Length (counts idx 3..9); checksum loop runs `Length+3` = idx 0..9 |
| 3 | 0x80 | SeqNum (constant 0x80 in ZHC) |
| 4 | mode | bit7 (0x80) = inching enabled (set unless `inching_control == "DISABLE"`); bit0 (0x01) = mode ON (set unless `inching_mode == "OFF"`) |
| 5 | channel | 0x00 = channel 1 (default), 0x01 only when `meta.endpoint_name === "l2"` |
| 6 | time lo | `round(inching_time_s * 2)` low byte, 0.5 s units |
| 7 | time hi | same value, `>> 8 & 0xff` |
| 8 | 0x00 | "Reserve" in ZHC |
| 9 | 0x00 | "Reserve" in ZHC |
| 10 | XOR | XOR of bytes 0..9 |

Little-endian time. Mode semantics (SONOFF's own words, CubeZ2mDeveloper in
https://github.com/Koenkk/zigbee2mqtt/issues/32669): mode OFF = turn on when triggered, then auto-off after
inching time (impulse); mode ON = turn off when triggered, then auto-on after inching time. Disable = bit7 clear.
Note a write that omits `inching_mode` sets bit0 (mode ON) because the check is `!== "OFF"`
(https://github.com/Koenkk/zigbee-herdsman-converters/issues/13383).

Range: min 0.5 s step 0.5; max 3599.5 s default (`maxTime = 3599.5`), 86399.5 s on MINI-ZBDIM, MINI-ZB1GSP,
MINI-ZB1GS (call sites `inchingControlSet({}, 86399.5)` L12173, L13315, L13882).

Possible ZHC bug (inference, UNVERIFIED on hardware): 86399.5 s = 172799 units needs 18 bits, but ZHC writes only
a 16-bit time (idx 6-7) and fixes idx 8-9 to 0. The ZHA quirk PR writes a 32-bit LE time over idx 6-9
(https://github.com/zigpy/zha-device-handlers/blob/bd08ef640536a709925b054bb4c145d82872885d/zhaquirks/sonoff/zbminir2.py#L218-L232),
suggesting idx 6-9 is one uint32. So units above 65535 (32767.5 s) would be truncated by ZHC. Whether the device
accepts them is UNKNOWN.

2-gang: channel byte only; ZHC maps endpoint name `l1` -> 0x00, `l2` -> 0x01; the command is sent on the
endpoint entity (`entity.command(...)`), the same endpoint 1 serves both on MINI-ZB2GS (UNVERIFIED; the endpoint
used is whatever the Z2M endpoint_name resolves to). Exposes: `endpointNames: ["l1","l2"]` (L11970).
Other models have only channel 0x00.

Models using `inchingControlSet` at ZHC master (model, converter line; model found by nearest preceding
`model:`):

| Model | `inchingControlSet` call | max s |
|---|---|---|
| S60ZBTPF | L11362 | 3599.5 |
| S60ZBTPG | L11493 | 3599.5 |
| ZBMicro | L11640 | 3599.5 |
| ZBMINIR2 (white label MINI-ZBD, same fingerprint list L11651-L11652) | L11709 | 3599.5 |
| MINI-ZB2GS | L11970 (l1, l2) | 3599.5 |
| MINI-ZBDIM | L12173 | 86399.5 |
| BASIC-ZB1GSP | L12917 | 3599.5 |
| MINI-ZB1GSP | L13315 | 86399.5 |
| MINI-ZB1GS | L13882 | 86399.5 |
| S61SZBTPB | L14297 | 3599.5 |

MINI-ZBDIM (a dimmer) is on the list but not in the brief. All other 0xFC11 `protocolData` command declarations
(L12887, L13288, L13855, L14087) are the same command redeclared for per-model custom clusters.

## 2. Readback and device responses

ZHC: no read path. The converter has no `convertGet`, `fromZigbee: []` (L2771-L2775), the 0xFC11 attribute list
(L2270-L2312) has no inching attribute (it has networkLed 0x0001, backLight 0x0002, radioPower 0x0012,
delayedPowerOnState 0x0014, delayedPowerOnTime 0x0015, externalTriggerMode 0x0016, detachRelayMode 0x0017,
deviceWorkMode 0x0018, ... 0x5001/0x5011-0x5013 motor, 0x7004-0x700b energy, 0x4001-0x4006 dimmer), and
`commandsResponse: {}` (L2317), so ZHC defines no inbound 0xFC11 command at all. `rg 'protocolDataResponse'`:
no hit. Z2M error for a get: "No converter available for 'get' 'inching_control_set'"
(https://github.com/Koenkk/zigbee-herdsman-converters/issues/13383).
Also note attribute 0x0017 `detachRelayMode` is a different thing from SubCmd 0x17; do not confuse.

zigbee-herdsman: no 0xFC11 / protocolData definition in core; the cluster exists only through ZHC's
`deviceAddCustomCluster`. (`gh search code --repo Koenkk/zigbee-herdsman fc11 / protocolData`: no hits.)

Device -> host report: a candidate exists, UNVERIFIED. ZHA PR #5317 (open) parses an inbound manufacturer-specific
command 0x01 on 0xFC11 with args `[0x01, 0x17, n, ...]`: `mode_byte = args[5]`, `timeout = LE uint32
args[6:10]`, enable = bit7, mode = bit0
(https://github.com/zigpy/zha-device-handlers/blob/bd08ef640536a709925b054bb4c145d82872885d/zhaquirks/sonoff/zbminir2.py#L264-L288;
test frame `01 17 01 80 00 81 05 00 00 00`, a synthetic test, not a capture). Evidence it is real is thin:

- Author z-qj: "The current device firmware version does not report the inching setting ... please upgrade to
  1.1.0" and "The inching readout still depends on firmware 1.1.0"
  (https://github.com/zigpy/zha-device-handlers/pull/5317). ZBMINIR2 v1.1.0 OTA release notes (zigpy-ota #373,
  https://github.com/zigpy/zigpy-ota/pull/373) list double-click/long-press events, Scenes cluster and On-with-
  Timed-Off, and say nothing about inching readout. The author is the same user who submitted the OTA.
- Reviewer AnomalRoil (same PR): on his device the quirk set timeout and behavior correctly but "it's not
  reading the settings properly and reports 'unknown' for inching mode and that inching is disabled whereas it's
  now enabled and actually is working." He proposed a patch; no follow-up confirming a successful read. His
  firmware version is not stated.
- No Z2M/ZHC issue or sniff showing an eWeLink hub reading inching, and no Sonoff public Zigbee doc found.
  Request-side read subcommand: UNKNOWN. (Searched `gh search code` for inching + 0xFC11 / protocolData; only
  the above quirks and ZHC.)
- ZHC has no code consuming such a report even with firmware 1.1.0 gates present (`zbminir2_external_switch_actions`
  gate, L1541).

Does the device answer the 0x17 write? ZHC leaves `disableDefaultResponse` at its default for a command with no
declared response (`hasResponse = false` -> default response requested,
https://github.com/Koenkk/zigbee-herdsman/blob/d6d2b39d202a463bd0aa97ea3052a16d89933ef4/src/controller/model/endpoint.ts#L1170-L1177).
`entity.command` awaits it, and the converter returns state only after it resolves, so a ZCL Default Response
(status unknown) is implied for the devices people use it on (no reported timeouts). UNVERIFIED: not captured.
A protocolData echo of the settings: UNKNOWN. The ZHA quirks avoid the question (`expect_reply=False`, #5317;
PR #5135 uses the normal cluster request).

SonoffLAN (Wi-Fi, analogous only): params `pulse` ("on"/"off") and `pulseWidth` in ms, 500 ms multiples, min
0.5 s, max 36000 s; the device reports them back as state and the integration requires `{"pulse":"on",
"pulseWidth":...}` together
(https://github.com/AlexxIT/SonoffLAN/blob/5f376c25c89fcd7cd198d2e4b6fb5bb4a24a2a6c/custom_components/sonoff/number.py#L42-L65,
https://github.com/AlexxIT/SonoffLAN/blob/5f376c25c89fcd7cd198d2e4b6fb5bb4a24a2a6c/custom_components/sonoff/core/devices.py#L164-L167).
Not the Zigbee protocol; no mapping to 0x17 is claimed.

## 3. Does onOff report off when inching fires?

Yes, with evidence from one user. Z2M log in https://github.com/Koenkk/zigbee-herdsman-converters/issues/13383
(ZBMINIR2/MINI-ZBD, fw 4096 = 1.0.0, Z2M 2.14.x): after arming inching mode OFF, 0.5 s, turning the switch on gives
`{"state":"ON"}` then 1 s later `{"state":"OFF"}`, i.e. the device sends an onOff attribute report on auto-off.
Arming itself is "relay-neutral (no state change on the config write)" for mode OFF; mode ON (or the omitted
default) switches the relay ON immediately and reverts every OFF to ON after the inching time. MINI-ZBD config
shows onOff reporting bound (min 1 s, max 1800 s, change 0) in Z2M issue #32669. Other models: UNKNOWN (no log
found). The pair of reports ON then OFF at only 1 s spacing shows the min interval of 1 s did not suppress it; for
sub-second pulses (0.5 s) a report could be missed or coalesced: UNKNOWN.

## 4. Z2M over MQTT

Expose path: `zigbee2mqtt/<friendly_name>/set` with the composite (access SET only, write-only, no `/get`):

```json
{"inching_control_set": {"inching_control": "ENABLE", "inching_time": 0.5, "inching_mode": "OFF"}}
```

- `inching_control`: "ENABLE" | "DISABLE"; `inching_time`: seconds, 0.5-3599.5 (86399.5 on three models), step 0.5;
  `inching_mode`: "ON" | "OFF" (L2692-L2711).
- 2-gang: flat suffixed fields inside the composite: `inching_control_l1/_l2`, `inching_time_l1/_l2`,
  `inching_mode_l1/_l2`, and the converter reads them via `meta.endpoint_name` (L2718-L2726). Exact MQTT shape for
  l1/l2 (suffixed names inside one `inching_control_set`, or one composite per endpoint): UNVERIFIED; for
  multi-endpoint Z2M uses `exposeEndpoints` suffixes, see the Moes ZM4LT2 state in
  https://github.com/Koenkk/zigbee2mqtt/issues/32248 (a Tuya variant of the same expose name).
- State after write is optimistic: `return {state: {[key]: value}}` (L2760), so Z2M publishes the value you sent
  and nothing from the device. Confirmed by the log in #13383: publishing `inching_control: "ON"` was echoed
  back as `"ON"` (an invalid enum value that the frontend renders as off); the Z2M frontend then shows armed
  state wrongly. After a disarm the cache keeps leftover `inching_mode`/`inching_time`. Because there is no
  readback, Z2M's published value is the last write, not the device state. After pairing, the S60 shows inching
  "inactive" in the UI though it was active on the device, and re-applying fixed it
  (https://github.com/Koenkk/zigbee2mqtt/issues/31604).
- Generic path without the converter: yes, partially. ZHC prepends generic converters to every definition
  (index.ts L424-L435): `read`, `write`, `command` (key `command`), `zcl_command` (key `zclcommand`)
  (https://github.com/Koenkk/zigbee-herdsman-converters/blob/ed29f80014f11cd3234e0e7371d1aace44e08982/src/index.ts#L424-L435).
  `command` calls `entity.command(value.cluster, value.command, value.payload, options)` but its options come from
  `getOptions` which only lets `disableDefaultResponse` and `timeout` through from definition meta
  (toZigbee.ts L241-L248; utils.ts `getOptions`), so no manufacturer code is sent: not usable for 0xFC11 as is
  (UNVERIFIED on hardware; the device may or may not require the 0x1286 code). `zclcommand` takes `options` in
  the payload (toZigbee.ts L262-L280), so
  `{"zclcommand":{"cluster":"customClusterEwelink","command":"protocolData","payload":{"data":[...11 bytes...]},"options":{"manufacturerCode":4742}}}`
  to `zigbee2mqtt/<name>/set` should work on any definition that registers `customClusterEwelink` (i.e. models
  using `addCustomClusterEwelink`). The cluster name only resolves on those devices; the `frametype` default is
  SPECIFIC, as needed. UNVERIFIED on hardware. `read` / `write` generics cover 0xFC11 attributes but not this command.
  No `bridge/request/*` route exists for raw ZCL (UNKNOWN: not checked in the Z2M source).

## 5. ZHA

- Shipped quirk `zhaquirks/sonoff/zbminir2.py` (dev `19fa63e`): defines the 0xFC11 cluster
  (`cluster_id = 0xFC11`) and no inching or `protocolData`; same for `mini_zb2gs.py`.
- zigpy dev has no 0xFC11 cluster definition (only a test fixture in `tests/test_zcl.py` using it as an example
  manufacturer-specific id; `gh search code --repo zigpy/zigpy fc11`).
- Open PRs:
  - #5135 "Add inching support for Sonoff ZBMINIR2 / MINI-ZBD" (open, head `7f334282ae`, approved by uschindler
    with a CHANGES_REQUESTED round before it): matches Z2M; entities inching switch / time (0.5-3599.5) / mode;
    `InchingPayload` struct, `PROTOCOL_DATA_COMMAND_ID = 0x01`, `EWELINK_MANUFACTURER_CODE = 0x1286`; write-only
    (no report handler in the diff). One tester says it turns the relay into a momentary switch for a garage
    door. https://github.com/zigpy/zha-device-handlers/pull/5135
  - #5317 "Add inching, power-on delay and action events for Sonoff ZBMINIR2" (open, head `bd08ef6405`, needs
    changes): also adds readback parsing (see 2), unverified.
    https://github.com/zigpy/zha-device-handlers/pull/5317 (closed predecessor #5304)
  - #5155 (MINI-ZB1GP + MINI-ZB1GSP quirk, head `c23d616877`) and #5703 (ZBMicro turbo): no inching in the diff.
  - Issues #4890 (MINI-ZBDIM support) and #4667 (MINI-ZB2GS options) mention no inching.
- Other models (MINI-ZB2GS, ZBMicro, S60/S61, MINI-ZB1GS(P), BASIC-ZB1GSP): no ZHA inching quirk or PR found.

## 6. Firmware and known issues

- Gating: ZHC has no firmware gate on `inchingControlSet`; the gates at L1536-L1547 apply to external-switch
  actions (ZBMINIR2 >= 1.1.0, MINI-ZB2GS >= 1.1.2), not inching.
- ZBMINIR2/MINI-ZBD: reported working on fw 1.0.0 (build 4096) per #13383; Z2M #32669 (MINI-ZBD fw 1.0.0, 12 V DC supply) reports a garage-door relay triggering repeatedly in inching
  mode; another user could not reproduce on ZBMINIR2 1.0.8; SONOFF's team could not reproduce and attributed
  such repeats to external trigger mode mismatch (edge vs pulse switch) causing two triggers. Unresolved
  (https://github.com/Koenkk/zigbee2mqtt/issues/32669).
- Readback of inching: claimed to need ZBMINIR2 fw >= 1.1.0 (PR #5317 author), UNVERIFIED.
- S60ZBTPF/G: unrelated auto-off after ~10 s with no load was root-caused to the converter enabling minimum
  power/current thresholds at configure, not inching (https://github.com/Koenkk/zigbee2mqtt/issues/31604, ZHC PR
  #12065), but users also report `inching_control_set` "DISABLE" having no effect
  (https://github.com/Koenkk/zigbee2mqtt/issues/31799, closed as duplicate of #31604). Treat inching disable on
  S60 firmware 1.0.2 as unreliable until retested.
- Z2M UI wrong state: #13383 (open): "inching_control" echoed as "ON", no get, mode default.
- ZHC possible 16-bit truncation for > 32767.5 s on MINI-ZBDIM / MINI-ZB1GS(P): see 1.
- Per-model firmware that introduced inching, and any firmware that lacks it: UNKNOWN.
