# Zigbee "turn on for N seconds": call patterns across vendors (2026-11-14)

Research date: 2026-11-14. Scope: which wire call makes a given device run a timed-on, how Zigbee2MQTT (zigbee-herdsman-converters, ZHC) and ZHA (zigpy, zha-device-handlers) route it. Feeds the decision: per-vendor routing in the DeviceSide Z2M/ZHA adapters, or one call plus a vendor gate.

## 1. What the spec says (baseline every vendor is measured against)

Source: [NXP OnOffCommandHandler.c `eCLD_OnOffHandleOnWithTimedOffCommand` L725-L800](https://github.com/nxp-mcuxpresso/mcuxsdk-middleware-zigbee/blob/a41ed0b86713ebf63b3b95a13394ed7233a685c1/ZCL/Clusters/General/Source/OnOffCommandHandler.c#L725) and [NXP OnOff.c `eCLD_OnOffUpdate` L475-L507](https://github.com/nxp-mcuxpresso/mcuxsdk-middleware-zigbee/blob/a41ed0b86713ebf63b3b95a13394ed7233a685c1/ZCL/Clusters/General/Source/OnOff.c#L475). Both quote the spec in comments. Field layout: [zigpy `OnOff.ServerCommandDefs.on_with_timed_off`, `OnOffControl`](https://github.com/zigpy/zigpy/blob/64b51efe715b221db4edf05e8a0e176f1782a146/zigpy/zcl/clusters/general.py#L872).

- **Wire:** cluster `0x0006`, command `0x42`, payload `on_off_control:bitmap8` (bit 0 = Accept Only When On), `on_time:uint16`, `off_wait_time:uint16`, both in **tenths of a second**, valid range `0x0000`-`0xFFFE`. NXP answers `INVALID_VALUE` above `0xFFFE`. [spec via NXP]
- **Accept Only When On:** if the bit is set and OnOff is off, the command is discarded. [spec via NXP]
- **Off Wait Time guard:** if OffWaitTime > 0 and the device is off, it only sets `OffWaitTime = min(OffWaitTime, field)` and **does not turn on**. Otherwise it sets `OnTime = max(OnTime, field)`, sets `OffWaitTime = field`, and turns on. [spec via NXP]
- **Timer:** every 0.1 s while on and OnTime > 0, OnTime decrements. When it reaches 0, OffWaitTime is set to 0 and OnOff to off. While off with OffWaitTime > 0, OffWaitTime decrements. The timer runs only while both are < `0xFFFF`. [spec via NXP]
- **Interaction:** plain `Off` sets OnTime = 0. `On` with OnTime == 0 sets OffWaitTime = 0. [spec via NXP]
- **The `max()` rule:** per spec, a second OnWithTimedOff cannot *shorten* a running timer, and `on_time: 0` should leave a light on with no timer. The **Hue rig contradicts both**: a new timer replaces the old one, longer or shorter, and `on_time: 0` turned the bulb off within 0.3 s ([rig], `docs/integrations/zha/internals.md`). So Hue firmware departs from spec here, and other vendors may follow the spec. [rig vs spec]
- **Who must implement it:** in the Matter data model, OnTime and OffWaitTime (and by extension 0x40-0x42) are mandatory only under the OnOff **Lighting (LT) feature**, FeatureMap bit 0, added in cluster revision 3 ([connectedhomeip `data_model/1.4/clusters/OnOff.xml`](https://github.com/project-chip/connectedhomeip/blob/master/data_model/1.4/clusters/OnOff.xml)). [spec via Matter] NXP's stack sets that FeatureMap bit when Level Control is present ([NXP OnOff.c L259](https://github.com/nxp-mcuxpresso/mcuxsdk-middleware-zigbee/blob/a41ed0b86713ebf63b3b95a13394ed7233a685c1/ZCL/Clusters/General/Source/OnOff.c#L259)). [code]
- **ZLL vs ZHA 1.2 vs Zigbee 3.0:** the 0x40/0x41/0x42 commands and the OnTime/OffWaitTime attributes came from the ZLL "enhanced" OnOff extensions and were later folded into the ZCL. ZHA 1.2-era devices often lack them. [inferred from history, spec text not fetched] The discovery data fits: pre-ZLL or ZHA-profile devices (CentraLite 4257050-RZHAC, Jasco 35938, SmartThings outletv4, Sengled E1F-N5E) advertise only `0,1,2` (or `0,1,2,64`). ZLL/Z3 lights (IKEA, LEDVANCE, Innr plug, iluminize) advertise `64,65,66`. [discovery] Plugs and relays are typically *not* "lighting" devices, so they have no obligation to implement 0x42. That is the root of most plug departures. [inferred]
- **Color/level while off:** Level and Color commands carry `OptionsMask`/`OptionsOverride`, where bit 0 is ExecuteIfOff ([zigpy `OptionsMask`, `Options` L972-L978](https://github.com/zigpy/zigpy/blob/64b51efe715b221db4edf05e8a0e176f1782a146/zigpy/zcl/clusters/general.py#L972)). Without the bit, a light that is off drops them. [code] OnWithTimedOff has no level or color field, so "color with timer" is always two calls. [spec via NXP]

## 2. How the stacks route `on_time`

### Zigbee2MQTT (ZHC)

- **Generic `tz.on_off`** ([ZHC/src/converters/toZigbee.ts#L16](https://github.com/Koenkk/zigbee-herdsman-converters/blob/afdaa028a0972d801da762196ddfb2df631ea0cc/src/converters/toZigbee.ts#L16)): when `state: ON` comes with `on_time` or `off_wait_time`, it sends `genOnOff.onWithTimedOff {ctrlbits:0, ontime: round(s*10), offwaittime: round(s*10)}`. It returns **no state**, which DeviceSide already records. [code]
- **Generic `tz.light_onoff_brightness`** ([toZigbee.ts#L1252](https://github.com/Koenkk/zigbee-herdsman-converters/blob/afdaa028a0972d801da762196ddfb2df631ea0cc/src/converters/toZigbee.ts#L1252)) claims `on_time`. **If `brightness` or `brightness_percent` is in the same message, `on_time` is silently dropped:** the converter sends `moveToLevelWithOnOff` and never reaches the `on_off` timed branch. Z2M runs one converter per message for both keys ([Z2M lib/extension/publish.ts L196-L205](https://github.com/Koenkk/zigbee2mqtt/blob/3c841fdfd66c92239921ef84fde8f039c64e1662/lib/extension/publish.ts#L196)). Exception: devices with `moveToLevelWithOnOffDisable` meta that change state. [code] DeviceSide already splits fields from the timer, which is correct.
- **Ordering:** for `state: ON`, Z2M sorts `state`/`brightness` *after* the other keys ([publish.ts L150-L155](https://github.com/Koenkk/zigbee2mqtt/blob/3c841fdfd66c92239921ef84fde8f039c64e1662/lib/extension/publish.ts#L150)). A `color` in the same message is therefore sent **before** OnWithTimedOff, with `optionsMask: 0` (no ExecuteIfOff), and a bulb that is off drops it. [code + rig for Hue drop]
- **No converter means silently plain-On:** if no converter in a definition claims `on_time`, Z2M logs `No converter available for 'on_time'` and continues ([publish.ts#L208](https://github.com/Koenkk/zigbee2mqtt/blob/3c841fdfd66c92239921ef84fde8f039c64e1662/lib/extension/publish.ts#L208)). `state: ON` still goes out as a plain `On`, so **the device stays on indefinitely** and the MQTT publish raises no error. [code] This is the main hazard for DeviceSide's single Z2M call. It hits every Tuya definition built with `onOffCountdown` (below).

### ZHA

- ZHA has no timed-on in its light/switch entities. DeviceSide calls `zha.issue_zigbee_cluster_command`, which goes through the device's (possibly quirked) cluster object. [code]
- **Tuya MCU (TS0601) quirks short-circuit it:** `TuyaOnOff.command` in [ZQ/zhaquirks/tuya/mcu/__init__.py#L398](https://github.com/zigpy/zha-device-handlers/blob/b07fa76876e081d48744968f9fb806e7f1fee0ee/zhaquirks/tuya/mcu/__init__.py#L398) and in [ZQ/zhaquirks/tuya/__init__.py#L625](https://github.com/zigpy/zha-device-handlers/blob/b07fa76876e081d48744968f9fb806e7f1fee0ee/zhaquirks/tuya/__init__.py#L625) translate only command ids 0/1 to a datapoint. Anything else, 0x42 included, gets a **locally fabricated `UNSUP_CLUSTER_COMMAND`** and never reaches the air. The quirk builder's default `TuyaOnOffNM` uses the MCU class. [code]
- **Tuya ZCL-native (TS011F, TS000x) quirks** use `TuyaZBOnOffAttributeCluster` ([ZQ/zhaquirks/tuya/__init__.py#L1055](https://github.com/zigpy/zha-device-handlers/blob/b07fa76876e081d48744968f9fb806e7f1fee0ee/zhaquirks/tuya/__init__.py#L1055)). It adds attributes 0x8000-0x8004 (child lock, backlight, power-on state, switch mode) and passes 0x42 to the device unchanged, so the device's Tuya countdown semantics apply. [code]
- **No quirk anywhere rewrites 0x42** (grep for `on_with_timed_off` across zhaquirks at the pinned commit: no hits). There are open PRs for Sonoff SWV ([#5378](https://github.com/zigpy/zha-device-handlers/pull/5378)) and Candeo C-ZB-SSFS ([#5412](https://github.com/zigpy/zha-device-handlers/pull/5412)). [code / report]
- Vendor auto-off attributes that ZHA quirks expose as entities: Third Reality `0xFF03` `countdown_to_turn_off` / `countdown_to_turn_on` (mfr `0x1407`) ([ZQ/zhaquirks/thirdreality/plug.py#L33](https://github.com/zigpy/zha-device-handlers/blob/b07fa76876e081d48744968f9fb806e7f1fee0ee/zhaquirks/thirdreality/plug.py#L33)), and Sinopé `timer` (`0x00A0`, manufacturer cluster) ([ZQ/zhaquirks/sinope/light.py#L139](https://github.com/zigpy/zha-device-handlers/blob/b07fa76876e081d48744968f9fb806e7f1fee0ee/zhaquirks/sinope/light.py#L139)). [code]

## 4. Distinct call patterns

Counting distinct **wire shapes and semantics** a sender must produce, there are **five**. Pattern A has one parameter variant.

**A. Standard ZCL OnWithTimedOff: one `0x0006/0x42`, `on_time` in tenths, `off_wait_time` 0, sent while off; turns on now.**
Philips Hue (rig models; not Lucca 1740193P0), IKEA TRÅDFRI (most; LED2005R5/LED2106R3 unicast in doubt; old WW fw 1.0.x-1.1.x don't advertise it), Ledvance/Osram/Sylvania lights, Innr, Ubisys, Inovelli, iluminize, Nordtronic, Sinopé SP2600ZB, Sonoff ZBMINIR2 ≥ 1.1.0, eWeLink CK-BL702 valves, Phoscon. Probably Gledopto, Müller Licht, Paulmann, Nanoleaf, Schneider, Legrand dimmers (no evidence either way).
- **A′, same shape with `on_time` in whole seconds:** Sonoff SWV. **Candeo** also needs a plain `On` first. Same command, different scaling, so it needs a per-model unit factor but no new route.

**B. Tuya ZCL countdown: plain `On` first, then `0x42` with `on_time = off_wait_time = N` whole seconds; a delayed toggle cancelled by any later On/Off.**
Tuya ZCL-native TS011F, TS0001-TS0004, TS0011, TS0726 and their white labels (Lidl HG06620, Nous, Moes, BSEED, Aubess, BlitzWolf, Zemismart, Avatto, Hobeian, Automaton…). `TYZB01_on_off` (Lonsonho, BlitzWolf) is a sub-variant with the fields split by direction. It's the same command id as A, but the semantics are so different that sending A's payload yields "nothing", "a delayed on 10× later" or "stays on", depending on firmware.

**C. Tuya datapoint countdown: `0xEF00` `dataRequest` with DP `state=on`, then DP `countdown` = N s.**
Tuya MCU TS0601 switches, plugs and valves. In ZHA, 0x42 never leaves the host (synthetic UNSUP).

**D. Persistent vendor auto-off ("inching") setting, then plain `On`.** This is a config write, not a per-call timer. It also changes what a physical press does, until reverted.
Sonoff `0xFC11` inching (S60ZBTPF/G, ZBMINIR2, MINI-ZB*, BASIC-ZB1GSP, ZBMicro, S61SZBTPB), Tuya `0xE000` `setInchingSwitch`, Third Reality `0xFF03` countdown attrs, Sinopé `timer` attr, Shelly "Auto off" (app only, not Zigbee).

**E. No device timer: plain `On`, then the host sends `Off` after N s.**
Sengled, Aqara/Lumi lights and plugs (as advertised), Sonoff S60ZBTPF (when not using inching), MINI-ZB2GS/S26R2ZB/S40LITE/ZBM5, Shelly S4SW, Osram SMART+ plug (Z2M report), ZHA 1.2-era devices (CentraLite, Jasco, SmartThings outlet).

**What this means for the decision** [inferred]: A and A′ cover the lighting classes. The rest is plugs and relays. For lights, "one call plus a vendor gate" holds, provided fields go before the timer. For plugs and switches the shape varies within a single brand (Sonoff alone spans A, A′, D and E) and within one model ID (Tuya by `manufacturerName` predicate). A vendor gate alone can't pick the call. It needs at least a device-class split (light vs plug), a model or manufacturer-name table for B/C, and a fallback to E (host timer) or "refuse". In Z2M specifically, the adapter can't trust that `on_time` reached the device: for every `onOffCountdown` or Tuya-DP definition, the publish silently becomes plain On.

**Cheap gates the adapter could read instead of a vendor list** [inferred, needs probing]:
1. ZCL Discover Commands Received on `0x0006`: 0x42 present or not. It separates A from E for many devices, but Tuya B devices also "accept" 0x42, and many Tuya devices don't answer discovery at all [discovery: Tuya rows show `confirmed: false`].
2. OnOff FeatureMap (`0xFFFC`) bit 0 (Lighting) on ZCL-8 stacks.
3. A Tuya `manufacturerName` prefix (`_TZ3000_`, `_TZ3210_`, `_TYZB01_`, `_TZE2xx_`) as a strong signal for B or C.
4. In Z2M, whether the definition exposes `countdown`: Z2M publishes its exposes in `bridge/devices`, a Tuya-countdown definition exposes it, and a generic one doesn't [code].

## 5. Color, brightness and the timer

- No ZCL command combines a timer with level or color. A timed-on with fields is always ≥ 2 commands. [spec via NXP]
- Z2M drops `on_time` when `brightness` is in the same message (`light_onoff_brightness`). [code]
- Z2M sends `color`/`color_temp` *before* `state` for an ON message, with `optionsMask 0`. A bulb that is off drops them unless its firmware ignores ExecuteIfOff (Gledopto turns on when color is set while off). [code]
- Hue: fields must land while on, or with ExecuteIfOff (LTA004/LWA012/LTA009/LCA016 store `MoveToLevel`/`MoveToColorTemp` with ExecuteIfOff; MoveToColor while off untested here). A later `On` or `moveToLevelWithOnOff` keeps the timer. [rig]
- Hue native `0xFC03` can set on, brightness, color and fade atomically but has no timer. The timer remains a separate 0x42. [code]
- Sengled: `MoveToLevel` while off jumps to 255. [rig]
- Tuya countdown (B): a `state` change after the countdown command **cancels** it (`on_off_countdown` comment: "'on/off/toggle' cancels 'onWithTimedOff'"). Fields sent as Level/Color commands are not On/Off, but `moveToLevelWithOnOff` might count as On. [code + inferred]
- Spec: `On` with OnTime == 0 clears OffWaitTime. `Off` zeroes OnTime. A plain `light.turn_off` ends a timer on any spec-following device. [spec via NXP]

## 6. Open questions only a hardware probe can settle

1. **Tuya ZCL countdown field semantics.** Reports disagree on which field the firmware reads (`on_time` in #22182, `off_wait_time` when off in #26004/#13491). For one TS011F and one TS0001, probe: (a) off + `{ontime N, offwait 0}`, (b) off + `{0, N}`, (c) on + `{N, 0}`, (d) on + `{N, N}` (Tuya's method), reading `onTime`/`offWaitTime` and state each second. It settles whether "plain On, then `{N s, N s}`" is the one safe Tuya B recipe, and whether DeviceSide's current call can switch a TS011F *on* 10× later (#22182 suggests it can; the rig saw "never switches on").
2. **Does Discover Commands Received predict behavior?** Probe one device per class that *advertises* 0x42 (IKEA LED2005R5, an Innr bulb, a Ledvance A60) and one that doesn't (Aqara T1, Sonoff MINI-ZB2GS): send 0x42 and record turn-on, turn-off time and the default-response status. Also probe IKEA LED2005R5/LED2106R3 by unicast vs groupcast (#29158).
3. **Spec `max()` vs Hue "replace".** On a non-Hue spec-following light (IKEA, Ledvance), does a shorter second timer shorten the run, and does `on_time: 0` leave the light on? This decides whether DeviceSide's "new call replaces timer" contract holds outside Hue.
4. Does the Accept-Only-When-On bit work on non-IKEA bulbs (Hue, Innr, Ledvance)? It matters only if the adapter ever extends a running timer without turning a light on.
5. Z2M Hue double-dispatch: does a `{"state":"ON","on_time":N}` publish to a Hue bulb on current ZHC send OnWithTimedOff twice (delegate mode) or Philips2 + 0x42 (`hue_native_control`)? A sniff or Z2M debug log settles it (it's harmless if Hue "replace" holds).
6. Sonoff: which current models (S60ZBTPF fw ≥ 2.0.3, ZBMINI-L2, ZBM5) gained 0x42 in recent firmware, as ZBMINIR2 did in 1.1.0; and does the `0xFC11` inching setting coexist with or override a 0x42 timer?
7. Tuya MCU (TS0601): per model, is the countdown DP a "toggle after N" or an "off after N", and does writing `state` cancel it?
8. Hue Lucca 1740193P0 (fw 1.104.2) on/no-off: firmware-specific, or a fixture class (outdoor wall lights) that ignores OnTime?
