## Short answer

Inching is a real, persistent, in-device auto-off (the relay turns itself off N seconds after turning on), but ZHC enables it on a hand-picked list (below), and hardware proof exists for only a few. Unit is whole seconds in a uint16 (1 to 65535 exposed); sub-second is not demonstrated anywhere. No ZHA quirk implements it for any Tuya switch.

## 2. Payload encoding and read decoding

Tuya doc, "DP19 Inching switch": client to server is command 0xFB on cluster 0xE000; server to client is attribute 0xD003 on 0xE000. Payload is `3 x n` bytes (n <= 6): byte 0 = channel id in bits 7..1 plus enable in bit 0; bytes 1-2 = duration, big-endian seconds (`00 3C` = 60 s). Examples: `01 00 3C` (1-gang enabled, 60 s); `00 00 3C 03 00 3C` (gang 1 disabled 60 s, gang 2 enabled 60 s). The doc table text says bit 0 "0: Enable, 1: Disable" but its own examples use 1 = enabled; ZHC and hardware reports follow the examples. Channel numbering: gang 2 is `03` (channel field 1, enabled), i.e. channel field = (gang - 1) << 1.

ZHC encoding (`valueConverter.inchingSwitch.to`, LIB L2901-2918, at the SHA): for each gang 1..6 where both `inching_control_<i>` and `inching_time_<i>` are given: `state = ENABLE?1:0; if i != 1: state += 2 ** (i-1)`; then `Buffer.from([state, secs >> 8, secs % 256]).toString("base64")`, concatenated across gangs. The base64 TEXT is then sent: `Buffer.from(<base64 string>)` as the payload of `manuSpecificTuya4.setInchingSwitch` (cmd 0xFB) on endpoint 1 always (LIB L3406-3419; code carries "TODO: correct?"). So on the wire it is ASCII base64, 4 bytes per gang (not the raw 3 bytes the Tuya doc shows). This works on hardware (ZHC#13118, #13879 and the TS0004 author's note "ASCII-base64 payload still check out", ZHC#13655 comment 2026-11-04). Whether the raw 3-byte form is also accepted: unknown, not tested anywhere I found.

Per-gang encoding defect: `2 ** (i-1)` equals the Tuya `(i-1) << 1` only for i = 1..3 (enabled values 1, 3, 5). For gang 4 it yields 9 (8|1) but the Tuya doc rule gives 7 (6|1); gangs 5/6 are wrong too. ZHC#13655 (open) states channel 4 must use 6/7 and fixes it. So 4-gang inching on master (`_TZ3000_tyg4yiat`, `_TZ3218_ya5d6wth`) likely mis-addresses gang 4. Inference from code plus PR text; not independently hardware-tested by us.

Multi-gang layout: each gang's record is concatenated in one command; only gangs where the user supplies both fields are included. On at least one firmware (TS0004 `_TZ3000_uz6ibhib`, fw 1.1.6) one write REPLACES the whole table (ZHC#13655 body), so a partial write can disable the other gangs. Whether that holds on other devices: unknown. Doc says nothing either way.

Read decoding (`valueConverter.inchingSwitch.from`, LIB L2921-2948 region; fz at L4071-4082): attribute `inching` 0xD003 is declared `CHAR_STR` (LIB L5798); `from` splits the string into 4-char base64 chunks, decodes each to 3 bytes: byte0 0 -> gang 1 DISABLE, 1 -> gang 1 ENABLE, otherwise gang = `trunc(log2(byte0)) + 1`, enable = `byte0 % 2`; time = `(b1 << 8) + b2`. Published as `inching_control_set.{inching_control_N, inching_time_N}`. Decode has the same gang >=4 skew as the encoder, and ZHC#13119 fixed an older utf8 bug (any low byte >= 0x80, i.e. about half of durations, corrupted the record before 2026-09-06; ZHC#8790 earlier "greater than 128 abnormal").

Read behaviour on bad devices: Z2M#32248 (Moes ZM4LT2, `inching_time_1: 29509`, phantom gangs 7/8/16/NaN) shows the base64 assumption breaking on at least one device; empty `inching_control_set: {}` in Z2M#31793 (`_TZ3210_6smingw0` on the generic TS0002, device lacks it); empty-string reads on `_TZ3000_p26flek3` and uz6ibhib.

Does ZHC read it back? Write-only converter: `tz.inchingSwitch` has `key: ["inching_control_set"]`, `convertSet` only, NO `convertGet` (LIB L3406-3419), the expose is `ea.SET`, and `convertSet` returns the written value as optimistic state. The `fz` decoder handles `attributeReport` and `readResponse`, so a value is published when the device reports 0xD003 or when something else triggers a read (ZH interview/attribute read). ZHC#13118 reports "after a restart each device reports its own persisted `inching` attribute"; the mechanism that issues that read is not visible in ZHC. Treat readback as best-effort and device dependent.

## 3. Duration limits

- Wire: uint16 big-endian seconds. Maximum 65535 s (about 18.2 h) by width. The Tuya doc gives no explicit min/max beyond the 2-byte field (only the example 60 s).
- Z2M expose (`tuyaExposes.inchingSwitch`, LIB L905-932): `inching_time` numeric, unit "seconds", min 1, max 65535, step 1. Converter does `Number.parseInt` so 0.1 becomes 0, no range validation on direct MQTT writes (ZHC#13655 comment).
- Z2M Nous breaker composite: minutes + seconds, `max(1, ...)`, capped 65535 (LIB L2995-3017).
- Hardware measured values: 5 s, 63 s (ZHC#13879, WHD02); 5 s (ZHC#13118, Mowe); 3600/3000/2400 s written and read back (ZHC#13119); 1 s on all four channels of uz6ibhib, 2 s, and 65535 accepted but no full-length run (ZHC#13655 table). Value 0 on uz6ibhib left the relay on (inching disabled in effect); 65536 and 0.1 rejected by the PR's own validation, not by the device.
- Sub-second: not supported by the encoding (unit is whole seconds); ZHC#13655 states "subsecond native operation was not demonstrated" and kept a software 150 ms HA pulse as the garage-door path. A fixed ~1 s pulse exists on some devices with no inching attribute at all (`_TZ3000_p26flek3`, 0.99 s measured, ZHC#13277), and MHCOZY-type 4-channel boards advertise a default 1 s on-board "inching mode" (Z2M#22840), which is a hardware mode switch, not this attribute. Whether any device accepts values below 1 s through some other unit: unknown.

## 4. Do non-enabled strings accept it?

Evidence is thin and mostly negative or silent:
- `_TZ3000_mzcp0of6` (enabled): reported no effect, Z2M#30056.
- `_TZ3000_gvoyoq2q` TS0003 (not enabled in ZHC, user forced `inchingSwitch: true`): "Inching is not working", Z2M#31804 (2026-04-27).
- `_TZ3000_p26flek3` TS0001: attribute reads empty, writes accepted without error, no effect, ZHC#13277.
- `_TZ3210_6smingw0` (Nova NTZB-01, ZHC#12038): generic TS0002 exposed inching but `inching_control_set: {}` and power-on writes UNSUPPORTED_ATTRIBUTE, Z2M#31793 (device is 1 switch + 1 socket).
- Moes ZM4LT2 `_TZ3000_criiahcg`: PR author listed "inchingSwitch - maybe works" (Z2M#28191); later inching state read-back is garbage (Z2M#32248). No test of actual auto-off reported.
- `_TZ3000_xfxpoxe0`, `_TZ3000_nwidmc4n`: not tried (Z2M#30017, #30018).
- The Tuya cloud schema shows `switch_inching` (String) on many modules (e.g. Z2M#28366 `_TZ3000_bvij6kod`, Z2M#30333 `_TZ3000_hznzbl0x` DP 19), so presence in the Tuya schema does not prove the Zigbee 0xE000 path works; `_TZ3000_hznzbl0x` is in ZHC without inching.
- Practical signal that a device supports it: read of 0xD003 returns a 4-char-multiple base64 string whose records decode; cluster 0xE000 listed in the endpoint is NOT sufficient (p26flek3 lists it). Z2M database entries for many TS0001-4 devices list `57344` (0xE000) and `57345` (0xE001) in inClusterList, so cluster presence is near universal and carries no signal.

## 5. Interaction with the one-shot countdown

- ZHC countdown is not an 0xF001 route: it is standard `genOnOff.onWithTimedOff` (cmd 0x42, `ctrlbits: 0, ontime = offwaittime = N`) with N 0..43200 s, read via `genOnOff` attribute `onTime` 0x4001 (LIB L3349-3405, L4055-4067); the code comment says the device reports `onTime` at every multiple of 60 s while counting; on/off/toggle cancels it. Exposed 0-43200 s (`tuyaExposes.countdown`, LIB L708).
- Inching is a separate attribute/command on 0xE000 and a separate persisted setting. Nothing in ZHC ties them together. No issue or PR I found tests both on one channel, so "does enabling inching disable or override countdown, and which wins if both run" is UNKNOWN. ZHC#13655 lists inching and countdown as independent controls on uz6ibhib and verified both separately (countdown 3 s auto-off; max `onTime=43200` read back; ordinary OFF cancels it) but not combined.
- State reporting after inching expiry: hardware shows the device turning itself off and Z2M seeing state OFF about N s later (ZHC#13118: ON at 13:02:53, OFF at 13:02:58 for 5 s, "unsolicited"; ZHC#13655: "unsolicited ON then automatic OFF reports" on 4 channels). So the off arrives as a genOnOff attribute report. ZHC#13655 also notes "immediate `onOff` reads can be stale on this firmware", so acceptance used reports, not reads. Whether every device reports (see section 6): unknown.

## 6. Reported bugs and firmware notes

- uz6ibhib (ZHC#13655, fw 1.1.6): one inching write replaces the whole table; empty 0xD003 read returns `""`; native duration 0 leaves relay on; OFF commands time out waiting for a default response unless `disableDefaultResponse` is set. All from the PR body/comments.
- Channel >= 4 encoding skew in master (section 2), ZHC#13655 open.
- utf8 corruption of durations with a low byte >= 0x80 until ZHC#13119 (merged 2026-09-06, so converters older than that mangle roughly half of all durations and every later gang record; also produced phantom gang 16).
- Z2M#32248: Moes ZM4LT2 garbage readback (wrong gang numbers, NaN, 29509 s) on a 2-gang device. Closed stale.
- Z2M#29398 (2025-11-02): after a Z2M update the expose vanished for `_TZ3000_nuenzetq` because the string fell off the generic TS0002 path; restored by a PR from andrei-lazarov. Shows how enablement is by string.
- Z2M#31799 (Sonoff S60ZBTPF) and Z2M#25303/#24407 (Sonoff ZBMINIR2) are Sonoff private-cluster inching, not Tuya 0xE000; out of scope.
- Firmware versions that ignore it: `_TZ3000_p26flek3` (version not stated), `_TZ3000_mzcp0of6` (not stated). WHD02 positive on fw `0122052017`. No more precise firmware matrix exists.

## 7. ZHA

No zha-device-handlers quirk implements inching for any Tuya switch/relay. `rg inching` over `zhaquirks/` finds no Tuya hits; the only 0xE000 handling is `TuyaZBE000Cluster` (`zhaquirks/tuya/__init__.py` L1169-1175), a named cluster with no attributes, used by `zhaquirks/tuya/ts000f.py` (`_TZ3218_hdc8bbha`, TS000F: power-on state, switch type). Related issues are requests only: ZHADH#3898 (`_TZ3000_dlhhrhs8` relay status and switch type, closed), ZHADH#3354 (TS0004 `_TZ3000_imaccztn`, closed). The Sonoff ZBMINIR2 inching PRs (ZHADH#5135, #5304, #5317) are the only inching work in ZHA and use Sonoff's cluster. ZHA therefore exposes no Tuya inching; that gap is the argument for implementing it from the 0xE000 attribute 0xD003 / command 0xFB path directly if DeviceSide wants coverage there.
