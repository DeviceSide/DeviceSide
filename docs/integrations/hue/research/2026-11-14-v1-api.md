# Hue v1 (round) bridge: can it support DeviceSide's dimming features?

Research note, 2026-11-14. Reading only: no probe was run on a v1 bridge.

**Question.** Can the Hue Bridge v1 (round, `BSB001`), which speaks only CLIP v1, support any of DeviceSide's dimming
features? If none, v1 is never supported.

**Answer.** Yes, a narrow subset. The documented v1 calls cover `raise_brightness`, `lower_brightness` and `stop`, and
probably `raise_saturation` and `lower_saturation`. Each would be degraded next to v2 (see the table). The flash-free
actions (`set_attributes`, `set_scene`), the timers (`turn_on_for`, `turn_off_for`), auto-off and auto-on, and hue
moves are not feasible. So the answer is not "none", and "never" can't rest on the API alone. I still recommend not
building v1, on other grounds: the bridge has been end of life since 2020, the feature set it could get is degraded,
and there is no way to collect evidence for it (Recommendation, below).

Scope: this note is about the v1 **bridge**. The v1 API running on a v2 (square) bridge is a different thing, which
DeviceSide doesn't need. Signify's statement that the v1 rule engine "will not be available long term" is about that
case. In Home Assistant, a config entry has `api_version` 1 only when the bridge has no CLIP v2: HA moves a v2-capable
bridge's entry to v2 on its own (`homeassistant/components/hue/migration.py`, which calls `is_v2_bridge`), and diyHue
emulates v2. In practice, `bridge_v1` means a round bridge.

## 1. What DeviceSide needs, per action (from v2)

Sources: [`docs/design.md`](../../../design.md), [`docs/action-behavior.md`](../../../action-behavior.md),
[`docs/integrations/hue/index.md`](../index.md), [`internals.md`](../internals.md) and
[`custom_components/deviceside/integrations/hue/*.py`](../../../../custom_components/deviceside/integrations/hue/), all
at `origin/claude/device-classes-5b-records`.

"Works" means the device does what users expect, quickly, with the behavior running on the device (it finishes even
with HA offline, and is never simulated with HA timers or loops: CONTRIBUTING, Development principles). The response
holds what core's rules require. On Hue v2, every command result is `sent`, never `confirmed`: the bridge acknowledges
its own copy of the state, not the bulb's. `get_attributes` returns values under core's names, and a `timer` only when
the device can report the time left.

| Action | What the v2 adapter relies on |
|---|---|
| `raise_brightness`, `lower_brightness` | One PUT of the end point plus `dynamics.duration`, which the bridge runs alone (`fade.py`). A room is one `grouped_light` PUT. A raise turns the light on. A lower to 0 is `on: false` with a duration, and the bridge keeps the stored brightness. A prediction cache and a report filter cover the bridge reporting the end value at once (`transition_cache.py`, `report_filter.py`). The event stream drives both. |
| `raise_saturation`, `lower_saturation` | One xy PUT with a duration: the light's hue at the target saturation, clamped to its gamut. |
| `stop` | `dimming_delta: {action: stop}`. v2 has no xy stop, so a color fade is halted by writing its predicted xy with duration 0. During a soft off the bridge refuses the stop, so it is cut with `on: true` at the predicted brightness (`stop.py`). Where a light halted is reported late or never, so DeviceSide predicts it. |
| `raise_hue`, `lower_hue` | Not built on Hue (NO_PATH): a hue rotation isn't a straight line in xy. |
| `set_attributes` | Writes to each light with no `on`. v2 stores what it is sent while the light is off (`bridge.py`, `write_light`). |
| `set_scene` | Reads the scene from aiohue and replays each light action as a light write, dropping `on: true`, so nothing turns on. Smart scenes are refused. |
| `get_attributes` | aiohue's copy of the state, kept current by the event stream, with predictions during a fade. Nothing is sent. |
| `turn_on_for`, `turn_off_for` | Not built on Hue (NO_PATH): the bridge's own timers keep running through a manual on or off (`docs/integrations.md`). |
| `set_auto_off`, `set_auto_on`, `clear_*` | Not built on Hue (NO_PATH): CLIP v2 has no rule engine. |

## 2. What the v1 bridge offers

The official v1 reference on developers.meethue.com needs a login, and that host, `www.home-assistant.io`,
`www.philips-hue.com` and `web.archive.org` were all unreachable from this session. The facts below come from two
copies of Signify's docs on GitHub (a 2013 copy of the original public site, and a recent copy of the v1 reference),
library source, and HA's code and docs at their current heads. Each fact names its source.

### Light and group state

- **`transitiontime`**: a `uint16` in units of 100 ms, default 4 (400 ms), not persistent. The maximum is 65535,
  about 109 minutes [S1 `01-lights-api.md`; S2 `1_lightsapi.md`; S1 `watch-that-transition-time.md`]. A v2 duration
  can run longer, so long sweeps would clamp, reported as `clamped_to`.
- **Increments** (since API 1.7): `bri_inc` and `sat_inc` take -254 to 254; `hue_inc` and `ct_inc` take -65534 to
  65534, and `hue_inc` wraps; `xy_inc` takes up to ±0.5 and "will stop at its gamut boundaries". Each one "stops any
  ongoing ... transition", and "setting a value of 0 also stops any ongoing transition". The bridge returns the value
  after the increment [S1 `01-lights-api.md`, lines 301–305; S6 `LightCommand.cs`]. So `bri_inc: 0` is a documented
  brightness stop, and `xy_inc`, `ct_inc` or `hue_inc` of 0 is a documented color stop. v2 has no xy stop at all.
- **No writes to an off light.** "A light cannot have its hue, saturation, brightness, effect, ct or xy modified
  when it is turned off. Doing so will return error 201", for lights and for groups alike [S1 `01-lights-api.md`
  line 333 and `02-groups-api.md` line 326; S2 `1_lightsapi.md` line 233; error text in S2 `8_errormessages.md`].
- **Groups**: `PUT /groups/<id>/action` takes the same fields, plus `scene` to recall a scene [S1 `02-groups-api.md`].
  A group command goes out as one Zigbee broadcast. `action` is "the last command that was sent to the whole group",
  not the group's state [S2 `2_groupsapi.md` line 62]. Rooms exist since API 1.11 and Zones since 1.30
  [S1 `02-groups-api.md`].
- **The reported state is a representation.** The bridge updates its own copy and sends Zigbee commands afterward,
  so the two "are not the same for a short period"; after a power cycle the copy "could take a few minutes" to
  correct itself [S2 `coreconcepts.md`, Representations]. So during a transition the bridge reports the end value at
  once, as v2 does, and it says nothing about where a stopped transition halted until it next reads the bulb. That
  last part is inferred, not measured.
- **Rate limits**: about 10 commands per second to `/lights`, at most 1 per second to `/groups`; about 25 Zigbee
  messages per second overall; commands over the limit are buffered (adding seconds of latency) and then dropped with
  error 901 [S1 `hue-system-performance.md`; S2 `coreconcepts.md`, Limitations]. aiohue's v1 client sends one request
  at a time, at most one every 0.25 s, shared with HA's polling, and retries on 429 or 503 [S3
  `aiohue/v1/__init__.py`].

### Scenes, schedules and rules

- **Scene recall** goes through `/groups/<id>/action {"scene": id}`, which applies the stored light states, `on`
  included. GroupScene arrived in API 1.28 [S1 `04-scenes-api.md`, `02-groups-api.md`]. v1 has no recall that leaves
  lights off, and the off-light rule rules out the replay workaround v2 uses. v1 has no smart scenes.
- **Schedules** support timers (`PT[hh]:[mm]:[ss]`, recurring or randomized), `status` and `autodelete`, with a
  bridge maximum of 100 [S1 `03-schedules-api.md`, `datatypes-and-time-patterns.md`, `bridge-maximum-settings.md`].
  These are the bridge timers DeviceSide already rejected for Hue: they keep running through a manual on or off.
- **Rules**: a rule condition's `address` is documented as a "Path to an attribute of a **sensor** resource". The
  operators are `eq`, `gt`, `lt`, `dx`, `ddx` and `stable`/`not stable` (1.13), plus `in`/`not in` (1.14). A rule
  holds at most 8 conditions and 8 actions [S1 `06-rules-api.md`, `bridge-maximum-settings.md`]. Light and group
  state conditions (`/groups/<id>/state/any_on`) appear in real-world rules: diyHue copies the Hue app's dimmer rules
  with them [S7 `functions/devicesRules.py`]. They are not in the documented condition table, though, and I found
  nothing showing that a round bridge accepts them.

### Polling, HA support and end of life

- **No push.** "V1 Hue bridges (round shape) are polled on an interval because the V1 API does not support push
  updates." HA "will continue to support the V1 Hue bridge as long as it is technically possible", with no scene
  entities (use `hue.hue_activate_scene`) and room entities only if the user opts in [S4 `hue.markdown`, lines
  67–84].
- **HA's v1 code** is still in core: `homeassistant/components/hue/v1/`, on aiohue 4.9.1's `HueBridgeV1`. It polls
  lights and groups every 5 s (`v1/light.py`, `SCAN_INTERVAL`) and refreshes 0.3 s after its own commands
  (`REQUEST_REFRESH_DELAY`). Groups need API 1.13 or later, and room entities are off by default
  (`DEFAULT_ALLOW_HUE_GROUPS = False`) [S5].
- **End of life**: Signify ended support for the v1 bridge on 30 April 2020. Its last firmware, 01043155 (22 June
  2020), stated that the v1 bridge gets no more updates, features or security patches and keeps working only locally
  [S9; secondary coverage S10]. These come from search summaries: I couldn't open philips-hue.com.
- **API level**: the round bridge's last API version is commonly given as 1.16.0 [S8 README: "v1.16.0 (v1
  bridge)"]. If so, it has `bri_inc` (1.7), Rooms (1.11), `ddx`/`stable` (1.13) and `in` (1.14), but no GroupScene
  (1.28) and no Zones (1.30). I did not check this against a real bridge.
- **Known quirk**: a light turned off with a transition comes back on at minimum brightness [S11, community docs].
  This is unconfirmed on the round bridge's last firmware.
- **hue_dimmer**, the project DeviceSide replaces, refuses v1 bridges too ("requires a Bridge V2 or Bridge Pro";
  `custom_components/hue_dimmer/bridge.py`) [S12], so dropping v1 breaks nothing for its users.

## 3. Verdict per action

| Action | Verdict | v1 call, and what the user would notice |
|---|---|---|
| `raise_brightness` | **Feasible, degraded** | `PUT /lights/<id>/state {"on": true, "bri": N, "transitiontime": T}`, or `/groups/<id>/action` for a room: one bridge-run fade. HA shows the end value at its next poll (up to 5 s; DeviceSide could ask HA's coordinator to refresh) and never shows the path. A raise from off probably starts at the stored brightness, not at the bottom, unless DeviceSide first sends `{"on": true, "bri": 1, "transitiontime": 0}`: two commands, unverified. Rooms are capped at 1 command per second and are opt-in in HA. Sweeps longer than 6553.5 s clamp. |
| `lower_brightness` | **Feasible, degraded** | `{"bri": N, "transitiontime": T}`. A lower to 0 % is `{"on": false, "transitiontime": T}`, which by community reports brings the light back at minimum brightness on its next on. v2 keeps the stored level instead. The fix (fade to `bri: 1`, then send off) needs an HA timer, which the principles forbid. A room with some lights off may get error 201 or partial effect: unverified. Same polling lag as a raise. |
| `stop` | **Feasible, degraded** | `{"bri_inc": 0}`, which is documented, to the light or the group. For a color fade, add `{"xy_inc": [0, 0]}` (documented, which beats v2). The result is `sent`, as on v2. Where the light halted isn't reported until the bridge re-reads the bulb, so DeviceSide's prediction stands in, as on v2, but corrections arrive only by polling. Halting DeviceSide's own soft off would need `{"on": true, "bri": predicted, "transitiontime": 0}`, because the bridge already reports the light off (error 201 otherwise): inferred. |
| `raise_saturation`, `lower_saturation` | **Feasible, degraded** (probe needed) | `{"xy": [x, y], "transitiontime": T}` on a lit light, as v2 does. v1 also offers `sat` plus `transitiontime`, but HA converts hs to xy for Philips bulbs, so xy is the safer call (S5, `v1/light.py`). The polling lag applies. The bridge doesn't clamp to gamut on a group, so DeviceSide would clamp per light (unverified). |
| `raise_hue`, `lower_hue` | **Not feasible** | v1 has no hue move at a rate. `hue` or `hue_inc` with `transitiontime` gives no control over direction, and v2's reason still holds: a rotation isn't a straight line in xy (DeviceSide NO_PATH). `effect: colorloop` cycles at a fixed, unset speed and has no limit. |
| `set_attributes` | **Not feasible** | Brightness, color and color temperature can't be written to an off light (error 201) [S1, S2]. Writing while off, so the light turns on without a flash, is the whole point of the action. |
| `set_scene` | **Not feasible** | Recall turns lights on, and replaying the scene's values per light hits error 201 while they're off. HA also creates no `scene` entities on v1 [S4], so the action has nothing to target. v1 has no smart scenes. |
| `get_attributes` | **Feasible, degraded**, but of little use | `GET /lights/<id>` returns `bri`, `xy` and `ct` whether the light is on or off. With no set-while-off and no timers on v1, it adds little over HA's own state. Values are as stale as the last poll unless DeviceSide sends its own GET, which spends the shared request budget. |
| `turn_on_for`, `turn_off_for` | **Not feasible** | A command plus a `PT` schedule is the same bridge timer DeviceSide rejected on v2: it keeps running through a manual on or off. Cancelling it on a manual change would need a rule conditioned on light state, which isn't documented [S1 `06-rules-api.md`]. |
| `set_auto_off`, `set_auto_on`, `clear_*` | **Not feasible as documented** | Building "off N seconds after any turn-on" needs a condition on a light or group's `on` with `ddx`. The documented conditions take only sensor attributes [S1]. The Hue app's undocumented `any_on` conditions might work on a round bridge, which only a probe would show. Even then the rule would see only turn-ons the bridge knows about, and the round bridge gets no fixes. |

## 4. Overall verdict and recommendation

**Can v1 support any of DeviceSide's dimming features? Yes: smooth brightness dimming and its stop, and probably
saturation fades, through documented calls** (`transitiontime`, `bri_inc: 0`, `xy_inc`). The fade runs on the bridge,
which satisfies "On the device". Everything that relies on writing while off, on timers or on rules is out, and so
are hue moves.

**Recommendation: don't build v1. Keep refusing it as `bridge_v1`, but give the real reason.** The premise "if none,
never" doesn't hold, so the decision rests on these grounds:

1. **End of life.** Since 2020 the bridge gets no firmware or security fixes. It has a small, shrinking user base,
   which fails the broad-appeal principle, and HA supports it only "as long as technically possible".
2. **Degraded where users look.** HA shows a fade's end, not its path, up to 5 s late. A soft off brings lights back
   at minimum (reported). Room commands are capped at 1 per second, and room entities are opt-in. All of it shares
   aiohue's queue of 4 requests per second with HA's polling.
3. **Half a feature.** Of the Hue features, only dimming would remain: no flash-free turn-on, no scenes, no timers.
   It also needs a second adapter stack (aiohue v1, polling, a coordinator hook in place of the event-stream report
   filter) with its own tests.
4. **No path to evidence.** Verifying it would take a round bridge on the rig or a maintainer who owns one. Without
   that, it stays Experimental indefinitely, and the open questions below need probes on real hardware.
5. **No parity loss.** hue_dimmer doesn't support v1 either.

Suggested doc change: `docs/integrations/hue/index.md` says v1 "lacks the v2 API and event stream DeviceSide uses".
That holds for flash-free turn-on and `get_attributes`, but not for dimming, which v1 can do with polling. A more
accurate line would be: v1 can't write to an off light or report changes without polling; Signify ended its support
in 2020; so it isn't supported.

If someone with a round bridge wants v1 later, the subset worth building is `raise_brightness`, `lower_brightness`
and `stop` on lights, flagged Experimental, after the probes listed below.

## 5. What I could not verify

- **The round bridge's actual API version and firmware.** 1.16.0 comes from a third-party README, and 01043155 as the
  last firmware comes from a search summary of Signify's release notes. Neither was checked on hardware or on the
  official page.
- **Whether `bri_inc: 0` halts a running `transitiontime` fade on a round bridge**, what `GET` reports after it, and
  how soon the bridge re-reads the bulb. Docs only.
- **Whether `xy_inc: [0, 0]` (or `bri_inc` combined with it in one PUT) halts an xy fade.** Docs only.
- **Raise from off**: whether `on` plus `bri` plus `transitiontime` fades from the stored level or from the bottom.
- **The minimum-brightness-after-soft-off bug** on the round bridge's final firmware: community report only.
- **A group `bri` write when some members are off**: error 201, partial effect, or members ignored.
- **Whether a round bridge accepts rule conditions on `/lights/<id>/state/on` or `/groups/<id>/state/any_on`**.
  This decides whether auto-off could ever be built.
- **The official v1 pages themselves.** developers.meethue.com, home-assistant.io, philips-hue.com and
  web.archive.org were blocked in this session. The Signify text quoted here comes from third-party copies (S1, S2),
  which match each other and the library doc comments (S6), but were not checked against Signify's own pages.
